Provability & Correctness

How to prove algorithms do the right things, don't do the wrong things, and finish in finite time.

EE Bridge

In hardware design, you don't just simulate — you formally verify. Timing analysis proves your circuit meets setup/hold constraints. Model checking proves your state machine can't deadlock. Equivalence checking proves your synthesized netlist matches your RTL. Software provability uses the same ideas: invariants (like timing constraints), termination (like guaranteed convergence of a PLL), and safety properties (like proving a latch-up can't occur).

The Three Questions of Correctness

Why "Correctness"?

From Latin correctus = made straight, set right. An algorithm is "correct" when its behavior has been "set right" — aligned with its specification. Partial correctness = "if it finishes, the answer is right" (partial because it doesn't guarantee finishing). Total correctness = partial correctness + termination = "it finishes AND the answer is right." The word "total" means the guarantee is complete — no caveats.

Every algorithm or system must answer three fundamental questions. These map directly to formal verification concepts you know from hardware:

The Three Pillars of Provability

Part 1: Loop Invariants — The Core Proof Technique

Why "Loop Invariant"?

"Invariant" from Latin in- (not) + varians (changing) = something that does NOT change. A loop invariant is a property that remains unchanged (invariant) across every iteration of a loop. Picture a spinning wheel: the axle doesn't move even though the wheel turns — the axle is the invariant. The invariant is the truth that survives every revolution of the loop.

A loop invariant is a property that is true before the loop starts, remains true after each iteration, and — combined with the loop's exit condition — proves the algorithm is correct. It's the single most important proof technique for algorithms.

EE Analogy: Timing Constraints

A loop invariant is like a setup/hold timing constraint in a synchronous circuit. Before each clock edge (iteration), the data must be stable (invariant holds). After each clock edge, the output settles to a valid state (invariant preserved). When the clock stops (loop ends), the final state is guaranteed correct. If the invariant ever breaks, the "circuit" produces garbage — just like a timing violation causes metastability.

The Three Parts of a Loop Invariant Proof

1
Initialization
The invariant is true before the first iteration.
EE: Reset state is valid.
2
Maintenance
If the invariant is true before iteration k, it's still true after iteration k.
EE: Each clock cycle preserves valid state.
3
Termination
When the loop ends, the invariant plus the exit condition implies the desired result.
EE: Final output meets spec after last clock edge.

Example: Binary Search

Let's prove binary search correctly finds a target in a sorted array, or correctly reports it's absent. 

def binary_search(arr, target):
    lo, hi = 0, len(arr) - 1
    # Invariant: if target exists, arr[lo] <= target <= arr[hi]
    while lo <= hi:
        mid = (lo + hi) // 2
        if arr[mid] == target:
            return mid
        elif arr[mid] < target:
            lo = mid + 1    # target can't be in arr[lo..mid]
        else:
            hi = mid - 1    # target can't be in arr[mid..hi]
    return -1

Part 2: Termination — Proving It Finishes

Why "Variant Function"?

"Variant" from Latin varians = changing — the opposite of "invariant." While an invariant stays the same, a variant changes (decreases) every iteration. Also called a "ranking function" because it ranks how far you are from termination — like a countdown timer. Picture an hourglass: the sand (variant) decreases each second, bounded by zero. When it runs out, the loop stops.

A termination proof shows that an algorithm always halts — no infinite loops. The key tool is a variant function (also called a decreasing measure or ranking function): a value that strictly decreases on every iteration and is bounded below.

EE Analogy: Energy Dissipation

Think of a variant function like energy in a damped oscillator. Each swing (iteration) dissipates energy (the variant decreases). Since energy is bounded below by zero, the oscillator must eventually stop. If you can show your algorithm has a "energy" that always decreases and can't go below zero, it must terminate. Similarly, a PLL converges because the phase error decreases each cycle — that's a variant function proof in hardware.

The Variant Function Recipe

1
Define the Variant
Find a non-negative integer expression V that depends on loop variables.
Example: V = hi - lo + 1 (search space size)
2
Show It Decreases
Prove V strictly decreases every iteration: V' < V.
Binary search: new space ≤ old_space / 2
3
Show It's Bounded
Prove V ≥ 0 always. Since a non-negative integer can't decrease forever, the loop must terminate.

Part 3: Pre/Postconditions — Design by Contract

Why "Design by Contract"?

Coined by Bertrand Meyer (Eiffel language, 1986). Named after legal contracts: a contract specifies obligations and guarantees for both parties. "Precondition" = Latin prae (before) + condition — what must be true before the function runs (the caller's obligation). "Postcondition" = Latin post (after) — what the function guarantees after it runs (the function's obligation). Like a contract between caller and function: "You give me sorted input, I guarantee the correct index."

Design by Contract (Bertrand Meyer, Eiffel language) specifies what a function requires and what it guarantees. This is the practical form of partial correctness proofs.

Design by Contract: Function as a Black Box

Contracts in Python

def binary_search(arr: list[int], target: int) -> int:
    """Find target in sorted array.

    Preconditions:
        - arr is sorted in ascending order
        - all elements are comparable

    Postconditions:
        - If returns i >= 0: arr[i] == target
        - If returns -1: target not in arr

    Invariant:
        - If target in arr, then arr[lo] <= target <= arr[hi]
    """
    # Validate precondition (in debug mode)
    assert arr == sorted(arr), "Precondition: arr must be sorted"

    lo, hi = 0, len(arr) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if arr[mid] == target:
            assert arr[mid] == target  # Postcondition
            return mid
        elif arr[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1  # Postcondition: target not in arr
Practical Tip: Assertions vs Production

Use assert for preconditions during development. In production, use explicit checks that raise proper exceptions. Python's -O flag strips all assertions. For critical contracts, use if not condition: raise ValueError(...).

Part 4: Safety vs Liveness Properties

Why "Safety" and "Liveness"?

Terms formalized by Leslie Lamport (1977). "Safety" = keeping safe, preventing harm. A safety property says "nothing bad ever happens" — like a safety rail preventing falls. If violated, you can point to the exact moment it went wrong. "Liveness" = being alive, making progress. A liveness property says "something good eventually happens" — the system is "live" (alive, active), not stuck. Named because a system that satisfies only safety but not liveness could simply do nothing — perfectly safe but dead. You need both: safe AND alive.

In distributed systems and concurrent programs, correctness splits into two orthogonal categories. Every property you want to prove about a system is either a safety property or a liveness property (or a combination).

Safety vs Liveness Properties
The Fundamental Trade-off

In an asynchronous distributed system, you often can't have both safety and liveness. This is the essence of the FLP impossibility result (Fischer, Lynch, Paterson, 1985): no deterministic consensus protocol can guarantee both safety (agreement) and liveness (termination) in an asynchronous system with even one faulty process. In practice, systems choose: Raft/Paxos sacrifice liveness (may block during leader election) to preserve safety (never disagree).

Part 5: Induction — Proving Recursive Algorithms

Why "Induction"?

From Latin inductio = leading into. Mathematical induction "leads you into" the truth of an infinite set of statements by proving just two things: the base case (the first domino falls) and the inductive step (if any domino falls, the next one falls too). "Structural induction" = induction that follows the structure of the data (tree, list, graph) rather than natural numbers. Named because the proof's structure mirrors the data's structure — recursive data gets a recursive proof.

Recursive algorithms are naturally proved by structural induction — the recursive structure of the algorithm mirrors the inductive structure of the proof.

The Induction Template

BC
Base Case
Prove the algorithm is correct for the smallest input (empty list, single node, n=0 or n=1).
IH
Inductive Hypothesis
Assume the algorithm works correctly for all inputs smaller than n.
IS
Inductive Step
Show that if it works for smaller inputs, it must work for input of size n. The recursive calls handle the smaller inputs (by IH), and the combine step preserves correctness.

Example: Merge Sort Correctness

def merge_sort(arr):
    if len(arr) <= 1:
        return arr            # BASE CASE: single element is sorted

    mid = len(arr) // 2
    left = merge_sort(arr[:mid])    # IH: correctly sorts left half
    right = merge_sort(arr[mid:])   # IH: correctly sorts right half

    return merge(left, right)       # IS: merging two sorted → sorted
The Proof

Base case: A single-element array is trivially sorted. ✓
Inductive hypothesis: Assume merge_sort correctly sorts any array of size < n.
Inductive step: For an array of size n, the two recursive calls sort arrays of size n/2 (by IH, both results are sorted). The merge function combines two sorted arrays into one sorted array (can be proved separately with a loop invariant). Therefore, the result is sorted. ✓
Termination: Each recursive call halves the input. Size is a natural number bounded below by 1. ✓

Part 6: Proving Systems Correct

Why "Model Checking" and "TLA+"?

"Model checking" — you build a model (simplified mathematical representation) of your system, then check every possible state it can reach. Named because it literally checks a model. Invented by Edmund Clarke and Allen Emerson (1981, Turing Award 2007). "TLA+" = Temporal Logic of Actions. "Temporal" = about time (Latin tempus). "Logic of Actions" = a logic for reasoning about actions that change state over time. The "+" was added by Leslie Lamport when he extended the original TLA. "Formal verification" = verification using formal (mathematical) methods, as opposed to informal testing. Named to distinguish rigorous mathematical proof from ad-hoc testing.

Proving individual algorithms is one thing. Proving entire systems — concurrent, distributed, with failures — requires different tools. Here's the practical toolkit, ordered from most to least formal:

The Verification Spectrum

TLA+ — The Staff Engineer's Secret Weapon

TLA+ (Temporal Logic of Actions) is a specification language created by Leslie Lamport. Amazon uses it extensively to verify distributed systems (DynamoDB, S3, EBS). It's the most practical tool for proving distributed system designs correct before writing code.

EE Analogy: TLA+ = SystemVerilog Assertions

TLA+ is to distributed systems what SystemVerilog Assertions (SVA) are to hardware. You write temporal properties ("if request is asserted, grant must follow within 3 cycles") and the model checker exhaustively verifies them against all possible execution traces. Just as SVA catches race conditions in RTL before tape-out, TLA+ catches concurrency bugs in system designs before deployment. 

---- TLA+ Specification: Simple Lock ----
(* Models a mutex ensuring mutual exclusion *)

VARIABLES lock, pc  (* lock holder, program counters *)

Init == lock = "free" /\ pc = [p \in Procs |-> "idle"]

Acquire(p) ==
    /\ pc[p] = "idle"
    /\ lock = "free"
    /\ lock' = p
    /\ pc' = [pc EXCEPT ![p] = "critical"]

Release(p) ==
    /\ pc[p] = "critical"
    /\ lock' = "free"
    /\ pc' = [pc EXCEPT ![p] = "idle"]

(* SAFETY: At most one process in critical section *)
MutualExclusion ==
    \A p, q \in Procs:
        (pc[p] = "critical" /\ pc[q] = "critical") => p = q

(* LIVENESS: Every request eventually gets the lock *)
StarvationFreedom ==
    \A p \in Procs: pc[p] = "waiting" ~> pc[p] = "critical"

Property-Based Testing in Python

For everyday development, property-based testing (using the hypothesis library) is the most practical form of provability. Instead of writing specific test cases, you describe properties that should always hold, and the framework generates hundreds of random inputs to try to break them. 

from hypothesis import given, strategies as st

# Property: sorting is idempotent (sorting a sorted list = same list)
@given(st.lists(st.integers()))
def test_sort_idempotent(xs):
    assert sorted(sorted(xs)) == sorted(xs)

# Property: sorted output has same elements as input
@given(st.lists(st.integers()))
def test_sort_permutation(xs):
    result = sorted(xs)
    assert len(result) == len(xs)
    assert sorted(result) == sorted(xs)  # same multiset

# Property: sorted output is actually sorted
@given(st.lists(st.integers(), min_size=2))
def test_sort_ordered(xs):
    result = sorted(xs)
    for i in range(len(result) - 1):
        assert result[i] <= result[i + 1]

# Property: binary search finds what's there, doesn't find what's not
@given(st.lists(st.integers(), min_size=1).map(sorted), st.integers())
def test_binary_search_correct(arr, target):
    result = binary_search(arr, target)
    if target in arr:
        assert result >= 0
        assert arr[result] == target
    else:
        assert result == -1
Key Properties to Test

Idempotency: f(f(x)) == f(x) — sorting, deduplication
Round-trip: decode(encode(x)) == x — serialization
Commutativity: f(a,b) == f(b,a) — set operations
Invariant preservation: invariant(f(x)) if invariant(x) — BST operations
Oracle testing: fast_impl(x) == slow_reference(x) — optimized algorithms

Part 8: Proving Greedy & DP Algorithms

Why "Exchange Argument"?

Named for the proof technique: you exchange (swap) one choice in an optimal solution with the greedy choice and show quality doesn't decrease. "Optimal substructure" = the optimal (best) solution has substructure (contains smaller solutions that are themselves optimal). Named because you can see the structure of smaller optimal solutions inside the big one — like a fractal where each piece mirrors the whole. "Overlapping subproblems" = the same subproblems overlap (appear multiple times) in different branches of the recursion. Named because the recursion tree has overlapping branches — the same subproblem computed repeatedly.

Greedy: The Exchange Argument

Greedy algorithms are notoriously tricky to prove correct. The standard technique is the exchange argument: show that any optimal solution can be transformed into the greedy solution without losing quality.

Exchange Argument: Greedy Proof Template

DP: Optimal Substructure + Overlapping Subproblems

To prove a DP solution is correct, show two things:

  1. Optimal substructure: An optimal solution to the problem contains optimal solutions to subproblems. (If you could improve a subproblem solution, you could improve the whole — contradiction.)
  2. Overlapping subproblems: The same subproblems appear repeatedly, so memoization/tabulation avoids redundant work. (This justifies using DP instead of plain recursion.)
Common Pitfall: Greedy ≠ Optimal

Many problems look greedy but aren't. The classic trap: coin change with denominations [1, 3, 4]. Greedy picks 4+1+1=3 coins for amount 6, but optimal is 3+3=2 coins. If you can't prove the exchange argument, it's probably not greedy — use DP instead.
