Systems Design

The Staff Engineer's Core Skill

System design is to software what schematic/architecture design is to hardware. At staff level, you will be expected to design systems from a blank whiteboard and to evaluate designs proposed by others. This is the single most important skill gap to close.

EE Bridge

Just as EE design starts with knowing your component library (op-amps, ADCs, MCUs, FPGAs), system design starts with knowing the software building blocks and when to use each one.

1.1 Databases

🗃
Relational (PostgreSQL, MySQL)
Structured tables with relationships, ACID transactions.

EE Analogy: SRAM — reliable, structured, consistent, but fixed format.

Use when: Structured data with relationships, need transactions (orders, users, inventory).

📄
Document (MongoDB, DynamoDB)
Schema-flexible JSON documents.

EE Analogy: Flash storage — flexible format, fast reads, variable structure.

Use when: Semi-structured data, rapid iteration, per-document access patterns.

⚡
Key-Value (Redis, Memcached)
Simple key->value store, in-memory.

EE Analogy: Register file — extremely fast, small, direct access by key.

Use when: Caching, session storage, rate limiting, real-time counters.

📊
Column-family (Cassandra, HBase)
Wide-column store, distributed writes.

EE Analogy: Distributed FIFO buffers — high write throughput, partitioned.

Use when: Time-series data, IoT telemetry, high write volume.

🔗
Graph (Neo4j, Neptune)
Nodes and edges with traversals.

EE Analogy: A netlist — natural for connection/relationship queries.

Use when: Social networks, recommendation engines, fraud detection.

🔍
Search (Elasticsearch)
Full-text search with inverted index.

EE Analogy: A lookup table / CAM — content-addressable search.

Use when: Search functionality, log aggregation, analytics.

Key Decision Framework

Is your data highly relational with transactions? -> Relational (PostgreSQL)
Is your data semi-structured and read-heavy?     -> Document (MongoDB)
Do you need sub-millisecond access by key?        -> Key-Value (Redis)
Is your write volume extremely high?              -> Column-family (Cassandra)
Are you querying relationships/connections?        -> Graph (Neo4j)
Do you need full-text search?                     -> Search (Elasticsearch)

What to Study

  • SQL: Be fluent. You need JOINs, GROUP BY, indexes, query plans.
  • Indexing: Understand B-trees (like a sorted lookup structure) and hash indexes.
  • Normalization vs denormalization: When to split tables vs duplicate data.
  • Sharding: How to split data across multiple database servers.
  • Replication: Leader-follower, leader-leader, quorum-based.
Why "Sharding"?

From "shard" — a broken piece of pottery or glass. You "shatter" one big database into smaller pieces, and each piece is a shard. Each shard holds a fragment of the whole dataset. The word instantly gives you the picture: one plate, broken into pieces, each piece still useful on its own.

1.2 Caching

EE Bridge

Caching is a buffer between a fast consumer and a slow producer — exactly like a CPU cache sits between the processor and main memory. Same concepts apply: cache hit, cache miss, cache invalidation, eviction policy.

Cache Strategies

Strategy How it works Tradeoff
Cache-aside (lazy loading) App checks cache first, loads from DB on miss Most common. You control what gets cached.
Write-through Write to cache and DB simultaneously Consistent but slower writes.
Write-behind Write to cache, async write to DB Fast but risk data loss.

Cache Invalidation (the hardest problem in CS)

  • TTL (Time-To-Live): Cache expires after N seconds. Simple, slightly stale.
  • Event-driven: Invalidate cache when the source data changes. Consistent but complex.
When to Cache

Read-heavy workloads where the same data is requested repeatedly and slight staleness is acceptable.

1.3 Message Queues and Event Streaming

Component What it is EE Analogy When to use
Message Queue (RabbitMQ, SQS) Point-to-point message delivery A FIFO buffer with flow control Decouple producer from consumer, async processing, load leveling
Event Stream (Kafka, Kinesis) Append-only log, multiple consumers A shared bus / backplane that multiple listeners can tap Event sourcing, real-time analytics, data pipeline between services

Delivery Guarantees

Guarantee Behavior EE Analogy
At-most-once Message may be lost. Fast but unreliable. UDP equivalent
At-least-once Message may be duplicated. Make consumer idempotent. TCP with retries
Exactly-once Hard to achieve. Usually at-least-once + idempotent consumer. Transactional protocol

1.4 Load Balancers and Reverse Proxies

Why "Load Balancer"?

Named for exactly what it does: it balances the load (traffic/work) across multiple servers. Picture a traffic officer at an intersection distributing cars across multiple highway lanes so no single lane gets jammed.

EE Bridge

Distribute incoming requests across multiple servers. Like a bus arbiter that distributes transactions to multiple slaves.

  • Round-robin: Simple rotation.
  • Least connections: Route to the server with fewest active connections.
  • Consistent hashing: Route based on request key. Same key always goes to same server (good for caching).
    Why "Consistent Hashing"?

    "Consistent" because when you add or remove a node, most keys stay mapped to the same node (consistent mapping). Regular hashing redistributes everything when the number of buckets changes; consistent hashing minimizes disruption. Think of it as adding a lane to a highway — only nearby traffic shifts, not the entire road network.

1.5 CDN (Content Delivery Network)

Why "CDN"?

Content Delivery Network — a network of geographically distributed servers that deliver content (images, videos, pages) from locations close to the user. The name says it all: it is a network whose job is delivering content fast.

Geographically distributed cache for static content. Like having local register copies instead of going to main memory every time. Reduces latency by serving content from the nearest edge server. CDNs rely on DNS to route users to the nearest edge server.

Why "DNS"?

Domain Name System — the system that translates human-readable domain names (google.com) into machine-readable IP addresses (142.250.80.46). "Domain" in networking means a realm of administrative authority. DNS is the internet's phone book: you look up a name, it gives you a number.

1.6 API Gateway

Single entry point for all clients. Handles: authentication, rate limiting, routing, request transformation. Like a protocol bridge / bus interface controller.

Part 2: Distributed Systems Fundamentals

2.1 CAP Theorem

Why "CAP Theorem"?

Named for the three properties: Consistency, Availability, Partition tolerance. Proposed by Eric Brewer in 2000 as "Brewer's conjecture," then formally proved as a theorem by Gilbert and Lynch in 2002. The acronym CAP captures the three-way trade-off — pick any two, but not all three.

The CAP theorem states that a distributed system can provide at most two out of three guarantees simultaneously:

  • Consistency (C): Every read receives the most recent write or an error. All nodes see the same data at the same time. If you write a value to one node, a read from any other node immediately returns that value. EE analogy: like a shared bus where all devices see the same signal level simultaneously — a single source of truth.
  • Availability (A): Every request receives a non-error response, regardless of the state of any individual node. The system always responds — it never says "I don't know" or times out. Every functioning node returns a result, even if it might be stale. EE analogy: like a redundant power supply — the system always provides power, even if one source is degraded.
  • Partition Tolerance (P): The system continues to operate despite network partitions — when messages between nodes are lost or delayed. A partition means some nodes cannot communicate with each other. Since networks are unreliable, partitions will happen — this is not optional in any real distributed system. EE analogy: like a circuit board where a trace is broken — some chips can't talk to each other, but the system must still function.
The Real Choice: CP or AP

Since network partitions will happen in any distributed system (you can't prevent them), P is not optional. The real choice is: during a partition, do you sacrifice Consistency (let nodes serve stale data so the system stays available — AP) or Availability (refuse to serve requests until nodes agree — CP)?

CP example: A banking system. During a partition, it's better to reject a transaction than to allow two nodes to independently approve the same withdrawal (double-spend).
AP example: A social media feed. During a partition, it's better to show a slightly stale feed than to show nothing at all.

CA (no partition tolerance) is only possible on a single node — in practice, this means a traditional non-distributed database like a single PostgreSQL instance. The moment you distribute across multiple machines, you must tolerate partitions.

CAP Theorem
EE Bridge

This is like a multi-master bus with arbitration. During a bus fault (partition), you either halt (CP) or let each master proceed independently and reconcile later (AP).

2.2 Consistency Models

Consistency Models Spectrum
  1. Linearizability: Acts as if there is a single copy. Most expensive.
  2. Sequential consistency: All nodes see operations in the same order.
  3. Causal consistency: Causally related operations are seen in order.
  4. Eventual consistency: All nodes converge eventually. Cheapest.

2.3 Consensus Protocols

Why "Paxos"?

Named after the Greek island of Paxos. Leslie Lamport wrote the original paper as a parable about a fictional "Paxon parliament" on the island, where legislators had to reach consensus despite frequently wandering off. The whimsical framing initially caused the paper to be ignored for years — but the algorithm became foundational.

Why "Raft"?

A play on "raft" — a simple boat — because it was explicitly designed to be a simpler, more understandable consensus protocol than Paxos. The creators (Ongaro & Ousterhout, 2014) made understandability the primary design goal. Also a backronym: Reliable, Replicated, Redundant, And Fault-Tolerant. If Paxos is a yacht, Raft is a raft — it gets you there, and you can actually build one.

EE Bridge

How do distributed nodes agree on a value? Same problem as clock synchronization in multi-clock-domain systems.

Protocol How it works Analogy
Paxos / Raft Leader-based consensus. Leader proposes, majority agrees. Master-slave with quorum ACK
Two-Phase Commit (2PC) Coordinator asks all nodes to prepare, then commit. Blocks if coordinator fails. Synchronous bus transaction with ACK
Saga pattern Sequence of local transactions with compensating actions on failure. Async transaction pipeline with rollback

2.4 Latency Numbers Every Engineer Should Know

L1 cache reference:                    1 ns
L2 cache reference:                    4 ns
RAM reference:                        100 ns
SSD random read:                   16,000 ns   (16 us)
HDD seek:                      2,000,000 ns   (2 ms)
Same-datacenter network round trip:  500,000 ns (0.5 ms)
Cross-continent network round trip: 150,000,000 ns (150 ms)
Why This Matters

If your service makes 5 sequential database calls at 0.5ms each, that is 2.5ms of latency from I/O alone. Can you parallelize them? Can you batch them? Can you cache them? This is your latency budget, exactly like timing analysis on a critical path.

Part 3: System Design Method

When designing a system (in an interview or at work), follow this process:

5-Step System Design Method

Step 1: Clarify Requirements (5 minutes)

  • Functional: What does the system do? (List the core features)
  • Non-functional: Scale (users, QPS), latency requirements, availability SLA
  • Constraints: Budget, team size, existing infrastructure

Step 2: Estimate Scale (5 minutes)

  • Users, requests per second, data size, storage growth rate
  • Read-heavy or write-heavy?
  • Bursty or steady traffic?

Step 3: High-Level Design (10 minutes)

  • Draw the major components (boxes) and data flow (arrows)
  • Identify the API endpoints
  • Choose the database type
  • Decide on synchronous vs asynchronous processing

Step 4: Deep Dive (15 minutes)

  • Pick the most complex or risky component
  • Design the data model (tables, fields, indexes)
  • Address: caching, partitioning, replication
  • Handle edge cases and failure modes

Step 5: Address Bottlenecks (5 minutes)

  • Single points of failure?
  • Scaling bottlenecks?
  • Monitoring and alerting?

Part 5: API Design — REST vs gRPC

EE Bridge

APIs are the interfaces between software components — like your pin-out and protocol specifications. REST is like UART/I2C — simple, universal, human-readable. gRPC is like SPI or PCIe — faster, binary, but needs more tooling. Staff engineers choose the right protocol for each boundary.

The Fundamental Difference

REST and gRPC solve the same problem — how do two services talk to each other over a network? — but they differ in their core philosophy:

R
REST: Resource-Oriented

"I want to interact with things."

You model your API as a set of resources (nouns) and use standard HTTP methods (verbs) to act on them. The network is treated like a document store — you GET, PUT, POST, DELETE resources at URLs.

Mental model: A filing cabinet. Each drawer is a resource collection. You open a drawer (GET), add a file (POST), replace a file (PUT), or shred one (DELETE).

g
gRPC: Action-Oriented (RPC)

"I want to call a function on another machine."

You define services with methods (like function signatures). The client calls a method as if it were a local function — the framework handles serialization, transport, and deserialization.

Mental model: A function call across machines. You write response = service.GetUser(request) and it feels local, but it executes remotely.

The Key Insight

REST says: "The network is a collection of documents. Navigate them."
gRPC says: "The network is invisible. Call functions on remote machines."
Both are valid. The choice depends on who is calling and what performance you need.

How REST Works

Why "REST"?

REpresentational State Transfer — coined by Roy Fielding in his 2000 PhD dissertation. "Representational" = you transfer representations of resources (JSON, XML), not the resources themselves. "State Transfer" = each request transfers enough state to be understood independently — the client and server pass state back and forth via these representations. The name encodes the core mechanism: moving representations of state over the wire.

REST (REpresentational State Transfer) is an architectural style built on HTTP. It's not a protocol — it's a set of constraints:

REST Request / Response Flow

REST Design Principles

# Resources are nouns, HTTP methods are verbs
GET    /users/{id}          # Read a user (idempotent)
POST   /users               # Create a user
PUT    /users/{id}          # Full replace (idempotent)
PATCH  /users/{id}          # Partial update
DELETE /users/{id}          # Delete (idempotent)

# Nested resources show relationships
GET    /users/{id}/orders   # List orders for a user
POST   /users/{id}/orders   # Create an order for a user

# Query parameters for filtering, pagination, sorting
GET    /users?role=admin&page=2&limit=50&sort=name

Key Properties

  • Stateless: Each request contains all information needed. Server stores no client state between requests.
  • Uniform interface: Standard HTTP methods + status codes. Every REST API works the same way.
  • Idempotent: GET, PUT, DELETE return the same result no matter how many times you call them. Safe to retry on network failures.
  • Cacheable: HTTP caching headers (ETag, Cache-Control) let intermediaries cache responses.
  • Human-readable: JSON payloads are text. You can debug with curl, browser dev tools, Postman.
  • Versioning: /v1/users — never break existing clients when evolving the API.

How gRPC Works

Why "gRPC"?

RPC = Remote Procedure Call — calling a function on another machine as if it were local. The "g" originally stood for Google (who created it), but it has become a running joke: each release assigns a different meaning (gRPC, Good, Green, Groovy...). Officially, "gRPC" is a recursive acronym: gRPC Remote Procedure Calls.

gRPC is a framework by Google built on HTTP/2 and Protocol Buffers (protobuf). You define your service in a .proto file, and the framework generates client and server code in any language.

gRPC: From Proto Definition to Running Code

The Proto File — Your Contract

// user.proto — defines the service, methods, and message types
syntax = "proto3";

// Message types (like structs in C)
message UserRequest {
  int32 id = 1;        // field number (not value)
}

message UserResponse {
  int32 id = 1;
  string name = 2;
  string email = 3;
  int64 created_at = 4;
}

// Service definition (like a class with methods)
service UserService {
  rpc GetUser(UserRequest) returns (UserResponse);
  rpc ListUsers(ListRequest) returns (stream UserResponse);  // server streaming
}
EE Analogy: Proto Files = HDL

A .proto file is like a Verilog module declaration. It defines the interface (ports/pins) strictly — input types, output types, method names. The protoc compiler is like a synthesis tool that generates the implementation wiring (client stubs + server skeletons) in your target language. You never manually serialize data — the generated code handles it, just like synthesis generates gate-level netlists from RTL.

Detailed Comparison

Aspect REST gRPC
Protocol HTTP/1.1 (or HTTP/2) HTTP/2 (required)
Data format JSON (text, human-readable) Protocol Buffers (binary, compact)
Schema OpenAPI / Swagger (optional) .proto files (required, strongly typed)
Code generation Optional (manual client code) Automatic (client + server stubs in any language)
Payload size Larger (~3-10x more bytes than protobuf) Smaller (binary encoding, no field names in payload)
Serialization speed Slower (JSON parse is CPU-intensive) Faster (~5-10x faster than JSON)
Streaming Workarounds (SSE, WebSocket, chunked) Native: client, server, and bidirectional streaming
Browser support Native (fetch, XMLHttpRequest) Requires grpc-web proxy (not native)

Versioning URL versioning (/v1/, /v2/) Field numbers in proto (backwards-compatible by design)
Error handling HTTP status codes (200, 404, 500...) gRPC status codes (OK, NOT_FOUND, INTERNAL...)
Multiplexing HTTP/1.1: one request per connection. HTTP/2: multiplexed. Always multiplexed (HTTP/2). Many calls on one connection.

When to Use What

API Protocol Decision Guide

Real-World Example: Both Together

Most production systems use both. Here's a common pattern:

Typical Architecture: REST at the Edge, gRPC Inside
The Rule of Thumb

REST at the edge, gRPC on the inside. Expose REST APIs for external consumers (browsers, mobile apps, third-party developers). Use gRPC for internal service-to-service communication where performance matters and you control both ends.

gRPC's Superpower: Streaming

REST is fundamentally request-response: client asks, server answers. gRPC supports four communication patterns:

1
Unary (like REST)
Client sends one request, server sends one response.
rpc GetUser(Req) returns (Resp)
2
Server Streaming
Client sends one request, server sends a stream of responses.
rpc ListUsers(Req) returns (stream Resp)
Use case: real-time feed, log tailing
3
Client Streaming
Client sends a stream of requests, server sends one response.
rpc UploadChunks(stream Chunk) returns (Resp)
Use case: file upload, batch insert
4
Bidirectional Streaming
Both sides send streams simultaneously.
rpc Chat(stream Msg) returns (stream Msg)
Use case: chat, multiplayer games, collaborative editing
EE Bridge: Communication Patterns

REST (unary) is like I2C — master initiates, slave responds, one exchange at a time.
Server streaming is like a UART TX — you request data and the device continuously sends readings.
Bidirectional streaming is like full-duplex SPI — both sides send and receive simultaneously on separate lines.
gRPC over HTTP/2 multiplexing is like a multi-lane PCIe bus — multiple independent streams on one physical connection.
