Sorting Algorithms

Sorting is the most studied problem in computer science. Dozens of algorithms, thousands of papers, and a fundamental truth: many problems reduce to sorting. Binary search requires sorted input. Two-pointer techniques need sorted arrays. Merge intervals? Sort by start time first. Sorting is not just an algorithm — it is a preprocessing step that unlocks other patterns.

EE Analogy: Signal Ordering

Think of sorting like ordering time-domain samples before an FFT. The raw ADC readings are useless until they are in the right sequence. Similarly, many algorithmic techniques only work after the data is sorted. Sorting is the "anti-aliasing filter" of algorithms — it removes the disorder so you can extract the signal.

Classification of Sorting Algorithms

C
Comparison Sorts
Compare pairs of elements (a < b?)

Bubble, Selection, Insertion, Merge, Quick, Heap. Theoretical lower bound: O(n log n).

N
Non-Comparison Sorts
Exploit structure of the data

Counting Sort, Radix Sort, Bucket Sort. Can beat O(n log n) by not comparing elements directly.

G
Graph-Based Ordering
Order by dependencies, not value

Topological Sort. Works on partial orders (DAGs) where not every pair of elements is comparable.

Part 2: Comparison Sorts

Every comparison-based sort answers the same question repeatedly: "Is element A less than element B?" The information-theoretic lower bound proves that any comparison sort must make at least O(n log n) comparisons in the worst case — because there are n! possible orderings and each comparison eliminates at most half.

1. Bubble Sort

Best: O(n) Avg: O(n²) Worst: O(n²) Space: O(1)
rarely used
Why "Bubble Sort"?

Named because smaller elements "bubble up" to the top (front) of the list, like air bubbles rising to the surface of water. Each pass, the largest unsorted element "sinks" to its correct position at the bottom.

Repeatedly walk through the array, swapping adjacent elements that are out of order. After each pass, the largest unsorted element "bubbles" to its correct position at the end. The simplest sort to understand and implement, but almost never used in practice due to poor performance.

EE Analogy

Like a bubble level — the heaviest elements "sink" to the bottom (end) of the array with each pass, just as a bubble rises to the top of a fluid because lighter elements float upward.

Code Template

def bubble_sort(arr):
    n = len(arr)
    for i in range(n):
        swapped = False
        for j in range(n - 1 - i):
            if arr[j] > arr[j + 1]:
                arr[j], arr[j + 1] = arr[j + 1], arr[j]
                swapped = True
        if not swapped:
            break  # already sorted
    return arr
When to Use

Almost never in production. Useful for: teaching, detecting near-sorted data (with early termination), or when simplicity is more important than speed on tiny inputs.

2. Selection Sort

Best: O(n²) Avg: O(n²) Worst: O(n²) Space: O(1)
simple
Why "Selection Sort"?

Named because each pass "selects" the minimum (or maximum) element from the unsorted portion and places it in position. You're literally selecting the next element.

Find the minimum element in the unsorted portion, swap it to the front. Repeat for each position. Always makes exactly n-1 swaps regardless of input — which is the minimum number of swaps possible to sort.

EE Analogy

Like scanning a voltage rail with a multimeter — you sweep across all test points, find the minimum reading, record its position, then physically move that component to the front of your sorted results.

Code Template

def selection_sort(arr):
    n = len(arr)
    for i in range(n):
        min_idx = i
        for j in range(i + 1, n):
            if arr[j] < arr[min_idx]:
                min_idx = j
        arr[i], arr[min_idx] = arr[min_idx], arr[i]
    return arr
When to Use

When the number of swaps matters (e.g., writing to flash memory where writes are expensive). Not stable, not adaptive. Otherwise, use insertion sort for small data.

3. Insertion Sort

Best: O(n) Avg: O(n²) Worst: O(n²) Space: O(1)
practical
Why "Insertion Sort"?

Named because each element is "inserted" into its correct position within the already-sorted portion. Like inserting a card into the right spot in a hand of sorted cards.

Build the sorted array one element at a time. Take the next unsorted element and insert it into its correct position in the sorted portion by shifting elements right. Excellent for nearly-sorted data — runs in O(n) when the array is almost sorted. Stable and in-place.

EE Analogy

Like inserting components into a sorted bill of materials — you take each new component, scan backwards through the sorted list to find where it belongs (by value or part number), shift everything down, and insert it. Hand-sorting resistors into a parts bin works exactly this way.

Code Template

def insertion_sort(arr):
    for i in range(1, len(arr)):
        key = arr[i]
        j = i - 1
        while j >= 0 and arr[j] > key:
            arr[j + 1] = arr[j]
            j -= 1
        arr[j + 1] = key
    return arr
When to Use

Small arrays (n < 20–50), nearly sorted data, online sorting (streaming input), or as the base case in hybrid sorts like Timsort. Python's sorted() uses insertion sort for small runs internally.

4. Merge Sort

Best: O(n log n) Avg: O(n log n) Worst: O(n log n) Space: O(n)
divide & conquer
Why "Merge Sort"?

Named because the key operation is "merging" two sorted halves into one sorted whole. The algorithm divides, then merges. Created by John von Neumann in 1945.

Divide the array in half recursively until each piece is a single element (trivially sorted), then merge sorted halves back together. Guaranteed O(n log n) in all cases. Stable. The gold standard for sorting linked lists and external data (data too large to fit in memory).

EE Analogy

Like a binary tree of comparators merging sorted streams. Imagine a tournament bracket where each match (merge step) combines two sorted sequences into one. Or think of a merge network in hardware — each level of the tree has parallel comparator chains that produce sorted outputs from sorted inputs.

Key Concept: Divide and Conquer

Merge sort is the canonical divide-and-conquer algorithm. This same strategy underpins binary search, quicksort, FFT (Cooley-Tukey), Strassen's matrix multiplication, and many recursive algorithms. Master the pattern here and you will recognize it everywhere.

Code Template

def merge_sort(arr):
    if len(arr) <= 1:
        return arr
    mid = len(arr) // 2
    left = merge_sort(arr[:mid])
    right = merge_sort(arr[mid:])
    return merge(left, right)

def merge(a, b):
    result = []
    i = j = 0
    while i < len(a) and j < len(b):
        if a[i] <= b[j]:
            result.append(a[i]); i += 1
        else:
            result.append(b[j]); j += 1
    result.extend(a[i:])
    result.extend(b[j:])
    return result
When to Use

When you need guaranteed O(n log n), stability, or are sorting linked lists (where merge sort is in-place!). Also ideal for external sorting (sorting data that does not fit in RAM — merge sorted chunks from disk).

5. Quick Sort

Best: O(n log n) Avg: O(n log n) Worst: O(n²) Space: O(log n)
most used
Why "Quick Sort"?

Named because it's empirically the quickest general-purpose sorting algorithm in practice (despite O(n²) worst case). Tony Hoare invented it in 1959 and named it for its speed.

Pick a pivot element, partition the array so everything less goes left and everything greater goes right, then recurse on both sides. Fastest in practice due to excellent cache locality and low constant factors. In-place (aside from recursion stack). Not stable.

EE Analogy

Like a comparator that separates signals above and below a voltage threshold. The pivot is your reference voltage — everything below goes to one output rail, everything above goes to the other. Then you recursively refine each rail with smaller thresholds until every element is in its exact position.

Code Template

def quick_sort(arr, lo=0, hi=None):
    if hi is None: hi = len(arr) - 1
    if lo < hi:
        p = partition(arr, lo, hi)
        quick_sort(arr, lo, p - 1)
        quick_sort(arr, p + 1, hi)

def partition(arr, lo, hi):
    pivot = arr[hi]  # last element as pivot
    i = lo - 1
    for j in range(lo, hi):
        if arr[j] <= pivot:
            i += 1
            arr[i], arr[j] = arr[j], arr[i]
    arr[i + 1], arr[hi] = arr[hi], arr[i + 1]
    return i + 1
Pitfalls
  • Worst case O(n²) on already-sorted data with naive pivot selection (first or last element)
  • Fix: use random pivot, median-of-three, or use nth_element / introselect
  • Not stable — equal elements may be reordered
  • Stack overflow on deeply nested recursion — use tail-call optimization or iterative version

6. Heap Sort

Best: O(n log n) Avg: O(n log n) Worst: O(n log n) Space: O(1)
guaranteed
Why "Heap Sort"?

Named because it uses a "heap" data structure (a complete binary tree with heap property) to sort. The heap gives you the max/min efficiently, and you repeatedly extract it.

Build a max-heap from the array (O(n)), then repeatedly extract the maximum and place it at the end. Guaranteed O(n log n) and in-place, but not stable and has poor cache locality compared to quicksort. The bridge to the heap/priority queue data structure.

EE Analogy

Like a priority decoder — the highest priority element always comes out first. A max-heap is a hardware priority queue: the root always holds the maximum, and when you remove it, the structure reorganizes itself in O(log n) time. Think of it as a binary tree where every parent node has a higher voltage than its children.

Code Template

def heap_sort(arr):
    n = len(arr)
    # Build max-heap (heapify from last parent down)
    for i in range(n // 2 - 1, -1, -1):
        sift_down(arr, n, i)
    # Extract max, place at end, re-heapify
    for i in range(n - 1, 0, -1):
        arr[0], arr[i] = arr[i], arr[0]
        sift_down(arr, i, 0)

def sift_down(arr, size, root):
    largest = root
    left = 2 * root + 1
    right = 2 * root + 2
    if left < size and arr[left] > arr[largest]:
        largest = left
    if right < size and arr[right] > arr[largest]:
        largest = right
    if largest != root:
        arr[root], arr[largest] = arr[largest], arr[root]
        sift_down(arr, size, largest)
When to Use

When you need guaranteed O(n log n) in-place and do not care about stability. Also useful when you only need the k largest/smallest elements (partial sort with a heap is O(n + k log n)). The heap data structure itself is essential for Dijkstra, Prim's MST, and priority scheduling.

Part 3: Non-Comparison Sorts

These algorithms break the O(n log n) barrier by not comparing elements at all. Instead, they exploit structural properties of the data (integer values, digit representation, bounded range). They achieve O(n) or O(nk) time, but with restrictions on input types.

7. Counting Sort

Time: O(n + k) Space: O(k)
O(n)
Why "Counting Sort"?

Named because it works by "counting" how many times each value appears. It counts occurrences, then uses the counts to place elements. Only works for integer keys in a known range.

Count the frequency of each value, then reconstruct the sorted output from the frequency table. Works only for integers in a bounded range [0, k). Stable (when implemented correctly with prefix sums).

Diagram: Counting Sort [4, 2, 2, 8, 3, 3, 1]

Count frequencies, then reconstruct 
def counting_sort(arr, max_val):
    count = [0] * (max_val + 1)
    for x in arr:
        count[x] += 1
    result = []
    for val, freq in enumerate(count):
        result.extend([val] * freq)
    return result

8. Radix Sort

Time: O(d · (n+k)) Space: O(n + k)
O(n)
Why "Radix Sort"?

"Radix" = base (from Latin "radix" = root). It sorts by processing one digit (of the number's radix/base) at a time. In base-10, radix=10. Named because it operates digit-by-digit in the number's radix.

Sort integers digit by digit, from least significant to most significant (LSD) or vice versa (MSD). Uses a stable sort (typically counting sort) as a subroutine for each digit. d = number of digits, k = base (e.g., 10).

Diagram: Radix Sort [170, 45, 75, 90, 802, 24, 2, 66]

Sort by ones, then tens, then hundreds 
def radix_sort(arr):
    max_val = max(arr)
    exp = 1
    while max_val // exp > 0:
        counting_sort_by_digit(arr, exp)
        exp *= 10
    return arr
When to Use Non-Comparison Sorts

When values are integers in a small range (counting sort), or when sorting fixed-width integers/strings (radix sort). Common in systems programming: sorting IP addresses, fixed-length record keys, or pixel values.

Part 5: Why Topological Sort is Fundamentally Different

Every sorting algorithm above works on total orders: given any two elements, you can always determine which comes first. The integers 3, 7, and 1 have a definite ordering (1 < 3 < 7). But what about tasks with dependencies?

Total Order vs. Partial Order

  • Total order: Every pair of elements is comparable. "Is 5 < 8?" always has an answer. Regular sorting operates here.
  • Partial order: Some pairs are comparable (A must come before C) but others are not (A and B are independent — either order is valid). Topological sort operates here.
EE Analogy: Gate Firing Order

In a combinational logic circuit, some gates must fire before others because their outputs feed into other gates' inputs. But independent gates — those on separate signal paths — can fire in any order. Topological sort gives you a valid "firing sequence" that respects all dependencies. The circuit's netlist is a DAG (directed acyclic graph), and topological sort linearizes it.

Key insight: If your "circuit" has a cycle, it is not combinational logic — it is sequential logic with latches or flip-flops. In graph terms, a cycle means no valid topological ordering exists. This is exactly deadlock detection!

Real-World Examples of Topological Sort

  • Build systems — Makefile dependencies: compile utils.o before main.o
  • Course prerequisites — take "Data Structures" before "Algorithms"
  • Task scheduling — dependencies between tasks in a project plan
  • Package installation — install dependency packages before the packages that depend on them
  • Spreadsheet evaluation — cell A1 depends on B2 and C3; evaluate B2 and C3 first

Kahn's Algorithm (BFS-Based Topological Sort)

The most intuitive approach: repeatedly find nodes with no incoming edges (in-degree 0), add them to the result, and remove their outgoing edges. If all nodes are processed, the result is a valid topological ordering. If some nodes remain, a cycle exists.

Code: Kahn's Algorithm

from collections import deque

def topological_sort_kahn(num_nodes, edges):
    # Build adjacency list and in-degree count
    adj = [[] for _ in range(num_nodes)]
    in_degree = [0] * num_nodes
    for u, v in edges:
        adj[u].append(v)
        in_degree[v] += 1

    # Start with all nodes that have no prerequisites
    queue = deque(i for i in range(num_nodes) if in_degree[i] == 0)
    result = []

    while queue:
        node = queue.popleft()
        result.append(node)
        for neighbor in adj[node]:
            in_degree[neighbor] -= 1
            if in_degree[neighbor] == 0:
                queue.append(neighbor)

    if len(result) != num_nodes:
        raise ValueError("Cycle detected! No valid ordering.")
    return result

DFS-Based Topological Sort

An alternative approach: run DFS on every unvisited node, and when a node finishes (all descendants visited), push it onto a stack. The stack, read top-to-bottom, is a valid topological order. This is the post-order reversal method. 

def topological_sort_dfs(num_nodes, edges):
    adj = [[] for _ in range(num_nodes)]
    for u, v in edges:
        adj[u].append(v)

    WHITE, GRAY, BLACK = 0, 1, 2
    color = [WHITE] * num_nodes
    order = []

    def dfs(u):
        color[u] = GRAY  # currently exploring
        for v in adj[u]:
            if color[v] == GRAY:
                raise ValueError("Cycle detected!")
            if color[v] == WHITE:
                dfs(v)
        color[u] = BLACK  # fully explored
        order.append(u)

    for i in range(num_nodes):
        if color[i] == WHITE:
            dfs(i)

    return order[::-1]  # reverse post-order
Cycle Detection = Deadlock Detection

If Kahn's algorithm finishes with fewer nodes than the graph has, a cycle exists — no valid ordering is possible. In the DFS approach, encountering a GRAY node (one currently on the recursion stack) means you have found a back edge, proving a cycle.

EE connection: This is exactly like detecting feedback loops in combinational logic. A combinational circuit MUST be a DAG. If the dependency graph has a cycle, you have unintentional sequential logic (a latch) — which is a serious design bug. In software, this manifests as deadlocks in lock ordering, circular imports, or infinite build loops.

Part 6: From Sorting to Problem Solving

Sorting as a Preprocessing Step

Sorting is often not the end goal — it is the first step that enables a faster algorithm. Spending O(n log n) to sort can save you from O(n²) brute force on the actual problem.
