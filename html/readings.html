Recommended Readings

A curated library of books, papers, and resources for the journey from EE-background engineer to staff-level SDE. Organized by topic with reading-order guidance tied to the 72-day plan.

How to Use This Page

Each resource includes a difficulty badge, a description of what you will gain from it, and a "Read this when..." note that maps to specific days in the 72-day study plan. You do not need to read everything — the Priority Stack at the bottom shows the five essential books if time is limited.

Section 1: Algorithms & Data Structures

Essential (Month 1)

Introduction to Algorithms (CLRS)

Thomas H. Cormen, Charles E. Leiserson, Ronald L. Rivest, Clifford Stein

Advanced

The definitive algorithms textbook. Dense, mathematically rigorous, and encyclopedic. Do not attempt to read cover-to-cover; treat it as a reference manual you consult when you need the canonical explanation of a technique. The proofs build real intuition if you invest the time.

Key chapters: Sorting (6-9), Dynamic Programming (15), Greedy Algorithms (16), Graph Algorithms (22-25).

EE Analogy

CLRS is the "Art of Electronics" of computer science. Just as Horowitz & Hill is the reference you keep on your bench for circuit design, CLRS is the reference you keep on your desk for algorithm design. You learn from it selectively, not sequentially.

Read this when...

Days 5-24 (Month 1). Look up specific chapters as you encounter each pattern in the study plan. Return to it throughout all three months as a reference.

Algorithm Design Manual

Steven S. Skiena

Intermediate

More practical and approachable than CLRS. Skiena's "war stories" show how algorithms solve real-world problems, giving you the contextual intuition that pure theory alone cannot. Part II is a catalog of algorithmic problems — invaluable when you recognize a problem shape but cannot name the technique.

The catalog format (indexed by problem type) trains the exact skill interviews test: given a novel problem, which algorithm family applies?

EE Analogy

Think of Part II like a component selection guide. Just as you would look up "I need a low-noise amplifier for 2.4 GHz" and find candidate topologies, you look up "I need shortest path with negative weights" and find Bellman-Ford.

Read this when...

Days 5-18 (Weeks 2-3). Read Part I chapters alongside your pattern study. Keep Part II as a permanent reference.

Grokking Algorithms

Aditya Y. Bhargava

Beginner

A visual, illustrated, beginner-friendly introduction to algorithms. If CLRS feels like drinking from a fire hose, start here. The hand-drawn diagrams make binary search, BFS, dynamic programming, and greedy algorithms click in a way that pseudocode alone never will.

Short enough to finish in a weekend. Gives you the scaffolding to make heavier books productive rather than overwhelming.

EE Analogy

This is your "Getting Started in Electronics" by Forrest Mims — the friendly illustrated guide that makes you comfortable with the territory before you crack open the heavyweight references.

Read this when...

Days 1-4 (Week 1). Read this first, before anything else. It builds the visual vocabulary the rest of the plan assumes.

Deep Dives (Month 2-3)

Algorithms (4th Edition)

Robert Sedgewick & Kevin Wayne

Intermediate

Excellent visualizations and clean Java implementations. Strikes the best balance between mathematical rigor and practical code. The companion website has animations for every algorithm — particularly useful for understanding sorting, trees, and graph algorithms.

Read this when...

Days 25-44 (Month 2). Use selectively to deepen understanding of algorithms you struggled with in Month 1.

Competitive Programming 3

Steven Halim

Expert

For going deep on problem-solving patterns and contest-style thinking. Covers advanced techniques like segment trees, suffix arrays, and network flow that occasionally appear in staff-level interviews. Only read this if you have exhausted the essentials and want a competitive edge.

Read this when...

Days 60+ (Month 3) or post-plan. Only after you are consistently solving medium LeetCode problems in under 25 minutes.

Online Resources

NeetCode.io

Curated Problem Lists

Beginner

Curated problem lists organized by pattern: Blind 75, NeetCode 150, and NeetCode All. The pattern-based organization mirrors this course's approach — study a pattern, then drill problems in that pattern. Video explanations for every problem.

Read this when...

Days 10+ (ongoing). Use alongside pattern study to find practice problems grouped by technique.

VisuAlgo.net

Algorithm Visualizations

Beginner

Animated visualizations for sorting, graph traversal, DP, and data structures. Step through algorithms frame by frame to build spatial intuition. Especially useful for BFS/DFS, Dijkstra, and tree rotations.

EE Analogy

This is the oscilloscope for algorithms — it lets you watch the signal (data) flow through the system (algorithm) in real time, catching behavior you would miss from code alone.

Read this when...

Days 5-18 (Weeks 2-3). Use whenever a pattern's behavior is hard to visualize from code.

LeetCode

Practice Platform

Intermediate

The standard practice platform. Focus on medium difficulty. Do problems by pattern (all sliding window, then all two pointers, etc.) rather than randomly. Random practice builds breadth without depth; pattern-grouped practice builds transferable recognition.

Read this when...

Days 10-72 (ongoing). 2-3 problems per day, grouped by the pattern you studied that week.

Section 2: Systems Design

Essential (Month 2)

Designing Data-Intensive Applications (DDIA)

Martin Kleppmann

Advanced

THE book for systems design. Kleppmann explains the fundamental trade-offs behind databases, replication, partitioning, transactions, batch/stream processing, and consistency models. It does not teach you to design a specific system; it teaches you to think about distributed data systems so you can design any system.

Recommended chapter order: 1, 2, 3, 5, 6, 7, 8, 9, then 4. Chapters 5-9 are the core — replication, partitioning, transactions, distributed systems challenges, and consistency/consensus.

EE Analogy

DDIA is like understanding semiconductor physics. It explains WHY systems behave the way they do, not just HOW to use them. Just as understanding carrier mobility and band gaps lets you predict transistor behavior in novel circuits, understanding replication log ordering and consensus protocols lets you predict system behavior under novel failure modes.

Read this when...

Days 25-40 (Weeks 5-7). One chapter per day. This is the single most important book in Month 2.

System Design Interview (Volumes 1 & 2)

Alex Xu

Intermediate

15+ end-to-end system design walkthroughs across two volumes. Each chapter takes a system (URL shortener, chat application, news feed, notification system, payment system, hotel reservation) and walks through requirements, estimation, API design, data model, high-level architecture, and deep dives.

Volume 1: URL shortener, consistent hashing, rate limiter, web crawler, notification system, news feed, chat system, search autocomplete.
Volume 2: Proximity service, nearby friends, Google Maps, payment system, hotel reservation, email delivery, S3-like object storage, real-time gaming leaderboard.

Read this when...

Vol 1: Days 30-44 (Weeks 6-8). Vol 2: Days 45-60 (Month 3). Read one design per sitting, then attempt it yourself from scratch before checking the walkthrough.

Building Microservices (2nd Edition)

Sam Newman

Intermediate

Practical guidance on when and how to decompose systems into services. Covers communication patterns (sync vs async), service boundaries, data ownership, deployment strategies, and the organizational implications of microservices. The second edition adds coverage of serverless and event-driven patterns.

EE Analogy

Microservices are like modular PCB design. Each board (service) has defined connectors (APIs), its own power regulation (independent deployment), and you can swap one board without redesigning the whole system — but the connector standards and signal integrity across boards become the hard problem.

Read this when...

Days 35-44 (Weeks 7-8). Read after DDIA, as the distributed systems foundations make microservices trade-offs much clearer.

Deep Dives

Database Internals

Alex Petrov

Expert

How databases actually work under the hood: B-trees, LSM trees, write-ahead logs, buffer management, consensus algorithms, and distributed transactions. Read this to move beyond "I know Postgres" to "I understand why Postgres makes the trade-offs it does."

EE Analogy

If DDIA teaches you digital logic design, this book teaches you the transistor-level implementation. It is the VLSI design course for databases.

Read this when...

Days 55+ (Month 3) or post-plan. Only after completing DDIA.

Understanding Distributed Systems

Roberto Vitillo

Intermediate

A concise, accessible overview of distributed systems concepts. Covers similar ground to DDIA but in roughly half the page count. Good as a complement or as a quicker alternative if time is extremely limited.

Read this when...

Days 25-35 (Weeks 5-6). Can be read in parallel with DDIA to get a second perspective, or as a substitute if DDIA's depth is too much.

Foundational Papers

Read 1-2 of these during Month 3. Each shaped how modern distributed systems are built. They are surprisingly readable.

Dynamo: Amazon's Highly Available Key-Value Store

DeCandia, Hastorun, Jampani, et al. (2007)

Advanced

Introduces consistent hashing, vector clocks, sloppy quorum, and hinted handoff. These techniques are the foundation for DynamoDB, Cassandra, Riak, and Voldemort. Understanding this paper lets you reason about eventual consistency in any system that uses these patterns.

EE Analogy

Consistent hashing is like a ring oscillator with tap points — data flows around the ring and gets captured by the nearest node, and adding/removing nodes only perturbs the local neighborhood, not the entire system.

Read this when...

Days 50-55 (Week 9). After DDIA Chapter 6 (partitioning), which provides the prerequisite context.

MapReduce: Simplified Data Processing on Large Clusters

Jeffrey Dean & Sanjay Ghemawat (2004)

Intermediate

The paper that launched big data processing. The concept is deceptively simple — map and reduce — but the engineering of fault tolerance, data locality, and stragglers is where the depth lies. Still the mental model behind Spark, Flink, and most batch processing.

Read this when...

Days 50-55 (Week 9). Pairs well with DDIA Chapter 10 (batch processing).

The Google File System

Ghemawat, Gobioff, Leung (2003)

Advanced

How to build a distributed file system that handles hardware failures as routine events. Chunk-based storage, single-master architecture with relaxed consistency, and append-optimized design. The concepts underpin HDFS and influence object storage systems like S3.

Read this when...

Days 55-60 (Week 10). After the Dynamo and MapReduce papers for context.

Raft: In Search of an Understandable Consensus Algorithm

Diego Ongaro & John Ousterhout (2014)

Intermediate

Consensus made understandable. Raft was explicitly designed to be easier to learn than Paxos while providing equivalent guarantees. Leader election, log replication, and safety are cleanly separated. Read this instead of the Paxos paper — it teaches the same concepts with far less pain.

EE Analogy

Consensus is the distributed systems equivalent of clock synchronization in multi-chip systems. Just as you need a clock tree to ensure all flip-flops sample data at the same moment, you need consensus to ensure all nodes agree on the order of operations.

Read this when...

Days 45-50 (Week 9). After DDIA Chapter 9 (consistency and consensus). The raft.github.io visualization is essential supplementary material.

Section 3: Software Engineering & Craft

Essential

Clean Code

Robert C. Martin

Beginner

Naming conventions, function design, comment philosophy, formatting, error handling, and the discipline of writing code that humans can read. Controversial in some circles — some examples are over-engineered — but the core principles (small functions, meaningful names, no side effects) are foundational.

Take the principles, not the dogma. The chapters on naming (2), functions (3), and error handling (7) are the most valuable.

EE Analogy

Clean code is like clean schematic design. Proper net labels, hierarchical sheets, consistent component naming, and clear signal flow make a schematic maintainable. The same discipline applied to code makes it maintainable. You would never ship a schematic with unlabeled nets; do not ship code with unlabeled variables.

Read this when...

Days 1-10 (Weeks 1-2). Read early so the principles inform all code you write during the plan.

A Philosophy of Software Design (2nd Edition)

John Ousterhout

Intermediate

Short (under 200 pages), opinionated, and brilliant. Ousterhout argues that the primary goal of software design is reducing complexity. Key concepts: deep modules (simple interface, complex implementation), information hiding, strategic vs. tactical programming, and the "define errors out of existence" principle.

Better than Clean Code for experienced engineers. Where Clean Code is about code hygiene, this book is about design judgment.

EE Analogy

"Deep modules" are like well-designed ICs. A UART chip has a simple interface (TX, RX, a few config registers) hiding enormous complexity (baud rate generation, framing, parity, FIFOs). A shallow module is like exposing every internal flip-flop as a pin — technically functional but a nightmare to use.

Read this when...

Days 30-35 (Week 6). Read before starting the capstone projects so you apply these design principles from day one.

The Pragmatic Programmer (20th Anniversary Edition)

David Thomas & Andrew Hunt

Intermediate

Timeless engineering wisdom distilled into practical principles. DRY (Don't Repeat Yourself), orthogonality, tracer bullets, pragmatic paranoia, design by contract, and "good enough" software. Each topic is a self-contained essay you can read in 10 minutes, making it ideal for daily study sessions.

The 20th anniversary edition is significantly updated with modern examples. The original (1999) holds up but the new edition is worth the upgrade.

Read this when...

Days 25-44 (Month 2). Read one or two topics per day as supplementary material alongside systems design study.

Refactoring (2nd Edition)

Martin Fowler

Intermediate

A catalog of refactoring patterns: extract method, move field, replace conditional with polymorphism, and dozens more. JavaScript examples in the 2nd edition, but the patterns are universal. The first three chapters on when and why to refactor are more valuable than the catalog itself.

The key insight: refactoring is not rewriting. It is a disciplined sequence of small, behavior-preserving transformations, each verified by tests.

Read this when...

Days 35-44 (Weeks 7-8). Read the introductory chapters, then use the catalog as a reference during the capstone projects.

Design Patterns

Head First Design Patterns (2nd Edition)

Eric Freeman & Elisabeth Robson

Beginner

Visual, engaging, and pedagogically effective introduction to design patterns. Uses the "Head First" learning methodology (images, puzzles, conversation) to make patterns stick. Covers Observer, Decorator, Factory, Singleton, Command, Adapter, Facade, Template Method, Iterator, Composite, State, Proxy, and MVC.

Read this when...

Days 30-38 (Weeks 6-7). Use this to learn the patterns. Then reference the GoF book for completeness.

Design Patterns (GoF)

Gamma, Helm, Johnson, Vlissides

Advanced

The classic reference that defined the field. 23 patterns organized as creational, structural, and behavioral. Dense and academic. Do not start here — use Head First to learn, then GoF as a reference when you need the precise definition or C++ implementation details for a specific pattern.

Read this when...

Days 35+ (reference only). Keep it on your desk. Look up specific patterns when you encounter them in code reviews or architecture discussions.

Testing

Unit Testing Principles, Practices, and Patterns

Vladimir Khorikov

Intermediate

The best book on testing strategy. Goes beyond "how to write a unit test" to answer the harder questions: what should you test? What makes a good test vs. a fragile one? When are integration tests better than unit tests? How do you avoid the trap of 100% coverage with 0% confidence?

Key framework: tests should verify observable behavior, not implementation details. Tests coupled to implementation break on every refactor and provide no safety net.

EE Analogy

Good tests are like test points on a PCB — you measure at the functional boundaries (input/output connectors, power rails, key signal paths), not at every internal node. Testing every internal node (implementation detail) creates a measurement setup that is more fragile than the circuit itself.

Read this when...

Days 20-25 (Weeks 4-5). Read before the capstone projects so you can apply proper testing strategy from the start.

Section 4: Staff Engineer & Leadership

Essential

Staff Engineer

Will Larson

Intermediate

Defines what staff engineers actually do through interviews with staff+ engineers at major companies. Covers the four archetypes (Tech Lead, Architect, Solver, Right Hand), how to operate at staff scope, and the transition from "doing the work" to "enabling the work." Short, practical, and immediately applicable.

Read this when...

Days 45-50 (Week 9). Read at the start of Month 3 when the focus shifts from technical skills to staff-level impact.

The Staff Engineer's Path

Tanya Reilly

Intermediate

A practical guide to the staff+ individual contributor track. Covers three pillars: big-picture thinking (technical vision, architecture), execution (project leadership, unblocking), and leveling up (growing other engineers, organizational influence). More actionable than Larson's book, with concrete exercises.

Read this when...

Days 50-60 (Weeks 9-10). Read after "Staff Engineer" for complementary perspectives. This is the more prescriptive of the two.

An Elegant Puzzle: Systems of Engineering Management

Will Larson

Intermediate

Even if you are not a manager, understanding how engineering organizations work is essential at staff level. Covers team sizing, tech debt prioritization, succession planning, and organizational design. Helps you understand why managers make certain decisions and how to influence those decisions effectively.

Read this when...

Days 55-65 (Weeks 10-11). Useful context for the staff-level skills modules on cross-team influence and technical direction.

Thinking in Systems: A Primer

Donella H. Meadows

Intermediate

Mental models for complex systems: stocks, flows, feedback loops, delays, and leverage points. Applies to everything from software architecture to team dynamics to organizational change. Teaches you to see the system beneath the symptoms — a skill that separates staff engineers from senior engineers.

EE Analogy

This is control systems theory applied to organizations and software. Feedback loops, gain margins, oscillation, and stability — the same concepts you learned in EE for PID controllers and op-amp circuits apply to understanding why adding engineers slows a project (negative feedback delay) or why a quick fix creates three new bugs (positive feedback).

Read this when...

Days 60-72 (Weeks 11-12). A capstone read that reframes everything you have learned through a systems-thinking lens.

Communication & Influence

Writing for Engineers

Gergely Orosz (articles & newsletter)

Beginner

Practical guidance on writing RFCs, design documents, and technical proposals. Orosz's "The Pragmatic Engineer" newsletter regularly covers how to write documents that drive decisions, not just describe systems. Free articles cover the essentials; the newsletter goes deeper.

Read this when...

Days 45-55 (Weeks 9-10). Read before writing your first RFC for the capstone project.

Turn the Ship Around!

L. David Marquet

Beginner

Leadership through intent-based leadership on a nuclear submarine. Replace "permission to..." with "I intend to..." Directly applicable to staff engineering: you propose direction and take ownership rather than waiting for permission. Teaches influence without authority — the core staff engineer skill.

EE Analogy

Intent-based leadership is like moving from a centralized clock distribution (everything waits for the master clock) to a source-synchronous design (each module drives its own timing alongside its data). It reduces the bottleneck at the center and increases throughput across the system.

Read this when...

Days 60-72 (Weeks 11-12). A light but transformative read for the final stretch.

Section 5: CS Fundamentals (for EE Background)

Essential

Operating Systems: Three Easy Pieces (OSTEP)

Remzi H. Arpaci-Dusseau & Andrea C. Arpaci-Dusseau

Intermediate

The best operating systems textbook, and it is free online. Organized into three sections: virtualization (processes, memory), concurrency (threads, locks, condition variables, semaphores), and persistence (I/O, file systems, disks). The writing is remarkably clear and engaging. Each chapter ends with practical exercises.

EE Analogy

This book bridges your EE knowledge directly to software. You understand how a processor executes instructions, how caches work, how interrupts fire. OSTEP shows you how the OS builds abstractions (processes, virtual memory, file systems) on top of that hardware. It is the firmware layer you already intuitively understand, made explicit.

Read this when...

Days 15-24 (Weeks 3-4). Focus on concurrency chapters (threads, locks, condition variables) as these directly apply to Python threading/asyncio work in Month 1.

Computer Networking: A Top-Down Approach

James F. Kurose & Keith W. Ross

Intermediate

Networking from the application layer down to the physical layer. The "top-down" approach means you start with HTTP and DNS (things you use daily) and progressively understand TCP, UDP, IP, and link-layer protocols beneath them. Excellent Wireshark labs available online.

Focus on: application layer (HTTP, DNS), transport layer (TCP, UDP, congestion control), and network layer (IP, routing).

EE Analogy

As an EE, you likely already understand the physical and link layers (RS-232, Ethernet PHY, modulation). This book fills the gap upward from there — how the upper protocol layers use the reliable byte streams your hardware provides to build application-level communication.

Read this when...

Days 20-30 (Weeks 4-5). Read the application and transport layer chapters. Skim the lower layers since your EE background already covers them.

The Linux Command Line

William Shotts

Beginner

Free online textbook covering the Linux shell from basics to shell scripting. If your Linux-fu needs sharpening, this fills the gap. Covers navigation, file manipulation, I/O redirection, pipes, permissions, processes, environment, and shell scripting with bash.

Read this when...

Days 1-10 (Weeks 1-2). Skim the basics (you likely know them), then focus on scripting, process management, and permissions chapters.

Python-Specific

Fluent Python (2nd Edition)

Luciano Ramalho

Advanced

Advanced Python mastery: the data model (dunder methods), sequences, dictionaries, functions as objects, decorators, closures, iterators, generators, context managers, concurrency (threads, processes, asyncio), and metaprogramming. This book transforms a Python user into a Python expert.

Read after you are comfortable with basic Python. Each chapter reveals a layer of the language you did not know existed.

EE Analogy

This is the datasheet deep-dive for Python. Just as reading the full STM32 reference manual reveals peripheral features you never knew existed (DMA chaining, timer synchronization, analog watchdogs), this book reveals Python features (descriptors, metaclasses, generator pipelines) that let you write radically better code.

Read this when...

Ongoing, starting Day 15. Read one chapter per week alongside other study. The concurrency chapters (19-21) align with Month 1 async/threading work; the data model chapters (1-5) are universally applicable.

Architecture Patterns with Python

Harry Percival & Bob Gregory

Advanced

Domain-Driven Design, event-driven architecture, CQRS (Command Query Responsibility Segregation), and the Repository pattern, all implemented in Python. Directly applicable to the capstone projects, especially the URL Shortener with Analytics (Project 2) which uses an event pipeline.

Read this when...

Days 40-55 (Weeks 8-10). Read before or during the capstone projects to apply these architectural patterns.

Python Concurrency with asyncio

Matthew Fowler

Intermediate

Deep dive into asyncio: event loops, coroutines, tasks, futures, synchronization primitives, async generators, and async context managers. Essential for building modern Python services. Covers the mental model shift from synchronous to asynchronous thinking.

EE Analogy

asyncio is cooperative multitasking — like a single-threaded interrupt-driven firmware architecture (super-loop with ISRs). Each coroutine yields at I/O boundaries (like returning from an ISR), and the event loop schedules the next ready coroutine (like the main loop polling flags).

Read this when...

Days 18-24 (Weeks 3-4). Aligns with the concurrency and asyncio modules in the daily plan.

The Priority Stack: If You Can Only Read 5 Books

Time is finite. If you can commit to only five books across the entire 72-day plan, these five deliver the highest return on investment, in this order:

The 80/20 Rule

These five books cover roughly 80% of the knowledge you need. The remaining 20+ resources on this page refine, deepen, and fill gaps — but these five are the load-bearing walls.

1. Grokking Algorithms

Beginner   Month 1, Week 1

Start here. It takes a weekend and gives you the visual vocabulary for every algorithm concept that follows. Without this foundation, heavier books will overwhelm rather than teach. Think of it as powering on the oscilloscope before you start debugging.

2. Designing Data-Intensive Applications

Advanced   Month 2, Weeks 5-7

The single most important book on this list. It rewires how you think about data, distribution, consistency, and system trade-offs. Every system design interview question becomes approachable after absorbing chapters 1-9. This is the book that turns "I can build a service" into "I can design a system."

3. A Philosophy of Software Design

Intermediate   Month 2, Week 6

Under 200 pages but permanently changes how you design interfaces and modules. The "deep modules" concept alone is worth the read. Apply its principles to every capstone project component. Short enough to read in two sittings.

4. System Design Interview, Volume 1

Intermediate   Month 2-3, Weeks 6-9

Bridges theory (DDIA) and practice (interviews). Each chapter is a complete design walkthrough you can study, then attempt yourself. The consistent framework (requirements, estimation, API, data model, architecture, deep dive) becomes your interview template.

5. The Staff Engineer's Path

Intermediate   Month 3, Weeks 9-10

Technical skills get you to senior. This book teaches what gets you to staff: technical direction, alignment across teams, and growing other engineers. Read it in Month 3 when you have the technical foundation to appreciate the organizational layer on top.

EE Perspective on This Stack

This priority stack mirrors how you would learn a new hardware domain: Grokking Algorithms is your eval board (get something running fast), DDIA is the IC datasheet (understand the component deeply), A Philosophy of Software Design is the design guide (best practices for integration), System Design Interview is the reference design collection (proven topologies you can adapt), and The Staff Engineer's Path is the project management handbook (shipping the product, not just designing the circuit).
