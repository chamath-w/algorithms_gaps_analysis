1. Topological Sort

Why "Topological Sort"?

"Topology" from Greek "topos" (place) + "logos" (study). Studies the structure of connections, not distances. A topological sort arranges a graph's nodes respecting their directed connections — the "topology" of dependencies.

A. The Problem This Solves

You have a set of tasks with dependencies: task C can't start until A and B are done. You need a valid execution order. This appears in build systems (compile order), course prerequisites, spreadsheet cell evaluation, and package managers.

Why can't simpler approaches work? You might think "just sort by number of prerequisites." But that fails -- two tasks with the same number of prerequisites might depend on each other transitively. BFS/DFS alone finds components or shortest paths but doesn't produce a valid dependency order. You need a structure-aware ordering that respects ALL edges in a directed acyclic graph (DAG).

Without this algorithm: You'd have to try every possible ordering and check validity -- O(n!) for n tasks.

B. The Core Insight

"Process nodes with no remaining dependencies first -- then remove their edges, revealing newly ready nodes."

Think of it as peeling an onion: the outermost layer has no inward dependencies. Remove it, and a new outer layer is exposed.

EE Analogy: Combinational Circuit Propagation

In a combinational logic circuit, gates fire in dependency order -- a gate's output is valid only when ALL its inputs are valid. Primary inputs (no dependencies) resolve first, then gates fed by those inputs, then the next level, and so on. This is exactly Kahn's algorithm: process gates with all inputs ready (in-degree 0), then propagate.

If there's a feedback loop (cycle), the circuit isn't combinational -- it's sequential and needs a flip-flop. Topological sort detects this: if you can't process all nodes, a cycle exists.

D. How It Works -- Step by Step

Approach 1: Kahn's Algorithm (BFS-based)

  1. Build the graph and compute in-degrees. For every edge u->v, add v to u's adjacency list and increment in_degree[v]. The in-degree tells you how many unresolved dependencies a node has.
  2. Seed the queue with all zero-in-degree nodes. These are your "primary inputs" -- tasks with no prerequisites. They're immediately ready to execute.
  3. Process the queue: dequeue a node, add it to the result order. This node is "done." For each of its outgoing edges (u->v), decrement in_degree[v] because one dependency is now resolved.
  4. If a neighbor's in-degree drops to zero, enqueue it. All its dependencies are now satisfied -- it's ready.
  5. Repeat until the queue is empty. If the result has fewer nodes than the graph, a cycle exists (some nodes' in-degrees never reached 0).

Approach 2: DFS Post-Order (Reverse)

  1. Run DFS from every unvisited node. Use 3-state coloring: WHITE (unvisited), GRAY (in current DFS path), BLACK (fully processed).
  2. When entering a node, color it GRAY. If you encounter a GRAY neighbor, you've found a back edge -- that's a cycle.
  3. After processing all of a node's children, color it BLACK and add it to the result. This is post-order: a node appears after all its descendants.
  4. Reverse the result. Post-order gives dependencies-last; reversing gives dependencies-first (topological order).

E. The Code

# Kahn's Algorithm (BFS-based topological sort)
from collections import deque, defaultdict

def topo_sort_kahn(num_nodes, edges):
    # Build adjacency list and count incoming edges for each node
    graph = defaultdict(list)
    in_degree = [0] * num_nodes

    for u, v in edges:       # u must come before v
        graph[u].append(v)
        in_degree[v] += 1

    # Start with all nodes that have no prerequisites (in-degree 0)
    # These are the "primary inputs" of our circuit
    queue = deque(i for i in range(num_nodes) if in_degree[i] == 0)
    order = []

    while queue:
        node = queue.popleft()
        order.append(node)

        # "Fire" this gate: reduce in-degree of downstream nodes
        for neighbor in graph[node]:
            in_degree[neighbor] -= 1
            if in_degree[neighbor] == 0:
                queue.append(neighbor)  # all inputs ready, gate can fire

    # If we processed fewer nodes than exist, there's a cycle
    return order if len(order) == num_nodes else []

F. When to Reach for This

prerequisite dependency ordering course schedule build order before/after constraints DAG valid sequence
G. Common Mistakes
  • Edge direction confusion: "A is a prerequisite of B" means edge A->B, not B->A. Think "arrow points to the thing that depends."
  • Forgetting disconnected components: You must seed the queue with ALL zero-in-degree nodes, not just one.
  • Using 2-state visited for DFS cycle detection: In directed graphs, you need 3 states (WHITE/GRAY/BLACK). A node can be visited but not "in the current path." Only a GRAY->GRAY edge indicates a cycle.
H. Memory Palace Anchor

Picture a combinational logic circuit on a PCB. The primary inputs (DIP switches, sensor pins) light up first. Then the first row of AND/OR gates fires. Then the second row. Layer by layer, the signal propagates until it reaches the output LEDs. If you trace it and find a wire going backwards (a cycle), the circuit needs a clock -- it's no longer purely combinational.

Topological sort = forward signal propagation in a combinational circuit.

2. Dynamic Programming (Bottom-Up Tabulation)

Why "Dynamic Programming"?

Richard Bellman chose "dynamic" to sound impressive to his boss who hated "research." "Programming" meant scheduling/planning (like "linear programming" = linear planning). Really means "multi-stage optimization by breaking into overlapping subproblems."

A. The Problem This Solves

Optimization problems where the solution depends on solutions to smaller subproblems, and those subproblems overlap (the same subproblem gets computed many times). Classic examples: minimum cost, maximum profit, number of ways to reach a goal.

Why can't simpler approaches work? Greedy fails when the locally optimal choice doesn't lead to the global optimum. Brute force explores exponentially many paths. You already understand top-down memoization (recursion + cache), which is great. Bottom-up is the SAME computation, but iterative.

Without bottom-up DP: Top-down memoization hits Python's recursion limit (~1000 deep), can't do space optimization (rolling arrays), and has function call overhead.

B. The Core Insight

"Build the answer from smallest subproblems upward, filling a table. The dependency graph of subproblems tells you the fill order."

If top-down asks "what do I need?" and works backward, bottom-up says "I'll compute everything I might need, starting from what I know."

EE Analogy: Circuit Simulation -- Forward vs. Backward

Top-down (memoization) is like starting at the output pin and asking "what feeds this gate?" Then for each input, "what feeds THAT gate?" You trace backward recursively. If the same intermediate signal appears in multiple paths, you cache it so you only compute it once.

Bottom-up (tabulation) is like SPICE simulation: start from the known inputs (base cases), compute every gate's output level by level, until you reach the final output. You never ask "what do I need?" -- you just fill in the truth table from left to right.

Both give the same answer. Bottom-up is more systematic, doesn't blow up the call stack, and you can often optimize memory by keeping only the last row of the table (like only needing the previous pipeline stage, not the whole history).

D. How It Works -- Step by Step

The Bridge from Top-Down to Bottom-Up

  1. Start with the recurrence you already know. For Fibonacci: fib(n) = fib(n-1) + fib(n-2). For LCS: dp[i][j] = dp[i-1][j-1]+1 if chars match, else max(dp[i-1][j], dp[i][j-1]).
  2. Identify the base cases. These are the subproblems you can solve without recursion. For Fibonacci: fib(0)=0, fib(1)=1. For LCS: dp[0][j]=0, dp[i][0]=0.
  3. Determine the fill order. Each cell depends on cells that come "before" it in some sense. For 1D: left to right. For 2D LCS: each cell depends on the cell above, to the left, and diagonally above-left -- so fill top-to-bottom, left-to-right.
  4. Create the table and fill base cases. For 1D: dp = [0] * (n+1). For 2D: dp = [[0]*(m+1) for _ in range(n+1)].
  5. Fill the table using the recurrence, iteratively. Replace recursive calls with table lookups. The values are already there because you filled in order.
  6. The answer is in the table at dp[n] or dp[n][m].

Why Bottom-Up Over Top-Down?

  1. No stack overflow: Python's default recursion limit is ~1000. Bottom-up uses a loop, not the call stack.
  2. Space optimization: If each row only depends on the previous row, you can keep just two rows (or even one row with careful indexing). Top-down can't do this easily.
  3. No function call overhead: Iterating is faster than recursive function calls, even with memoization.
  4. Clearer complexity analysis: The number of iterations is explicitly visible from the loop bounds.

E. The Code

# Side-by-side: Top-Down vs Bottom-Up for Fibonacci

# TOP-DOWN (what you already know)
def fib_top_down(n, memo={}):
    if n <= 1: return n
    if n in memo: return memo[n]
    memo[n] = fib_top_down(n-1) + fib_top_down(n-2)
    return memo[n]

# BOTTOM-UP (the same computation, iteratively)
def fib_bottom_up(n):
    if n <= 1: return n
    dp = [0] * (n + 1)
    dp[0], dp[1] = 0, 1         # base cases
    for i in range(2, n + 1):
        dp[i] = dp[i-1] + dp[i-2]   # same recurrence, table lookup
    return dp[n]

# SPACE-OPTIMIZED (only need last 2 values)
def fib_optimized(n):
    if n <= 1: return n
    prev2, prev1 = 0, 1
    for _ in range(2, n + 1):
        prev2, prev1 = prev1, prev2 + prev1
    return prev1
# 2D Example: Longest Common Subsequence
def lcs(text1, text2):
    m, n = len(text1), len(text2)
    # dp[i][j] = LCS length of text1[:i] and text2[:j]
    dp = [[0] * (n + 1) for _ in range(m + 1)]

    for i in range(1, m + 1):
        for j in range(1, n + 1):
            if text1[i-1] == text2[j-1]:
                # Characters match: extend the LCS from diagonal
                dp[i][j] = dp[i-1][j-1] + 1
            else:
                # Don't match: take best of skipping either character
                dp[i][j] = max(dp[i-1][j], dp[i][j-1])

    return dp[m][n]

F. When to Reach for This

minimum cost maximum profit number of ways can you reach longest/shortest subsequence overlapping subproblems optimal substructure take or skip decision
G. Common Mistakes
  • Imprecise state definition: "dp[i] = best result" is too vague. Be precise: "dp[i] = max profit using items 0..i-1 with capacity W" vs "dp[i] = max profit ending at index i." These give different recurrences.
  • Wrong fill order: If dp[i][j] depends on dp[i-1][j-1], dp[i-1][j], and dp[i][j-1], you must fill top-to-bottom, left-to-right. Filling in the wrong order reads uninitialized values.
  • Off-by-one with 1-indexed dp: When dp has size (n+1), remember dp[i] typically corresponds to the first i elements, and dp[0] is the empty case.
  • Forgetting to consider ALL choices: At each state, enumerate every option (take/skip, use character/skip character) and pick the best.
H. Memory Palace Anchor

Picture a SPICE simulation of a pipeline ADC. Stage 1 samples the input (base case). Stage 2 reads stage 1's output and computes its value. Stage 3 reads stage 2. Each stage only needs the previous stage's result. You can throw away older stages once you're past them (space optimization). And you never need to "go back" -- the computation flows forward, filling in the table from left to right, input to output.

Bottom-up DP = forward SPICE simulation. Top-down = backward tracing from output to inputs.

3. Backtracking

Why "Backtracking"?

"Back" + "tracking" = tracking/tracing your steps backward. When you reach a dead end in the search tree, you backtrack (go back) to the previous decision point and try a different choice.

A. The Problem This Solves

Generating all valid configurations or finding a valid arrangement under constraints. Permutations, combinations, N-Queens, Sudoku, word search on a grid. Any problem where you build a solution piece by piece and need to explore all possibilities.

Why can't simpler approaches work? Brute force generates ALL possible configurations (e.g., all n! permutations) then filters valid ones. With n=20, that's over 2 * 10^18 configurations. Backtracking prunes early -- it never generates branches that already violate constraints, making it exponentially faster in practice.

Without backtracking: You'd enumerate every possibility. For 8-Queens, that's 8^8 = 16 million board configurations to check, vs roughly 15,000 with backtracking.

B. The Core Insight

"Build incrementally. Abandon a branch the moment it violates a constraint. Undo and try the next option."

The pattern is always: choose -> explore -> un-choose.

EE Analogy: Test Engineer Probing a PCB

Imagine debugging a multi-layer PCB. You start at the connector, trace signal path A. You probe a junction -- signal looks good. Continue down branch A1. Dead signal. You backtrack to the junction and try branch A2. Bad signal there too. Backtrack further to the connector, try signal path B.

You don't probe every single trace on the entire board. You follow a path, and the moment you find a fault, you backtrack to the last decision point. That's backtracking: systematic exploration with early abandonment.

D. How It Works -- Step by Step

  1. Define the decision space. At each step, what choices do you have? For N-Queens: which column to place the queen in the current row. For permutations: which unused element to place next.
  2. Choose: Pick an option and add it to the current partial solution.
  3. Check constraints (prune): Does this choice violate any constraint? If yes, skip it immediately -- don't recurse deeper. This is the pruning that makes backtracking efficient.
  4. Explore: Recursively solve the remaining subproblem with this choice in place.
  5. Un-choose (backtrack): Remove the choice to restore state, then try the next option. This is critical -- you must leave the state exactly as you found it.
  6. Base case: If the partial solution is complete (all queens placed, all slots filled), add a copy to results.

E. The Code

def solve_n_queens(n):
    result = []
    board = [-1] * n  # board[row] = column where queen is placed

    def is_safe(row, col):
        # Check against all previously placed queens
        for r in range(row):
            c = board[r]
            # Same column, or same diagonal?
            if c == col or abs(c - col) == abs(r - row):
                return False
        return True

    def backtrack(row):
        if row == n:
            result.append(board[:])   # COPY! Found a valid placement
            return

        for col in range(n):
            if is_safe(row, col):      # PRUNE: skip invalid placements
                board[row] = col       # CHOOSE
                backtrack(row + 1)    # EXPLORE
                board[row] = -1       # UN-CHOOSE (backtrack)

    backtrack(0)
    return result

F. When to Reach for This

all permutations all combinations all subsets generate all valid enumerate N-Queens / Sudoku word search constraint satisfaction
G. Common Mistakes
  • Forgetting to copy: result.append(current) appends a reference. When you later modify current, the result changes too. Always use current[:] or list(current).
  • Forgetting to un-choose: If you modify state before recursing, you MUST undo it after. Otherwise the next branch starts with corrupted state.
  • No pruning: Backtracking without pruning is just brute force with extra steps. The power comes from detecting invalid branches early.
  • Duplicate handling: For combination sum with duplicates, sort the input and skip candidates[i] == candidates[i-1] when i > start.
H. Memory Palace Anchor

Picture a maze-solving robot with one rule: when you hit a wall, back up to the last junction and try the next corridor. The robot marks each path it tries. When a path dead-ends, it reverses (un-choose), erases its marks (restore state), and takes the next untried corridor. It systematically explores every reachable path without ever going down the same dead end twice.

Backtracking = maze robot with wall detection (pruning) and junction memory (recursion stack).

4. Heap / Priority Queue

Why "Heap / Priority Queue"?

"Heap" = pile/mound. The binary tree looks like a pyramid/mound shape. "Priority" queue = items come out in priority order, not insertion order. Like a hospital triage queue.

A. The Problem This Solves

You need to repeatedly find the minimum (or maximum) element from a collection that changes over time -- elements are inserted and removed dynamically. Sorting doesn't work because the data is streaming, and you'd have to re-sort after every change.

Why can't simpler approaches work? An unsorted list gives O(1) insert but O(n) to find the min. A sorted list gives O(1) min but O(n) insert (shifting). A heap gives O(log n) for both operations -- the sweet spot.

Without heaps: Dijkstra's algorithm would be O(V^2) instead of O((V+E) log V). Finding the K-th largest element would require sorting the entire array every time a new element arrives.

B. The Core Insight

"A binary tree where every parent is smaller (or larger) than its children. Not fully sorted -- just enough structure to always know the extreme element."

The key: the heap property is weaker than full sorting. You trade the ability to find any element for faster insert/extract of the min or max.

EE Analogy: Priority Interrupt Controller

A priority interrupt controller (like the 8259 PIC) doesn't sort ALL pending interrupts. It just always knows which one has the highest priority. When a new interrupt arrives, the controller inserts it in O(log n). When the CPU finishes handling one, it extracts the next-highest priority in O(log n). The controller maintains just enough order to serve the most urgent request -- exactly like a heap.

D. How It Works -- Step by Step

Heap Insert (heappush)

  1. Add the new element at the end of the array (last position in the complete binary tree).
  2. Bubble up (sift up): Compare with parent at index (i-1)//2. If the new element is smaller than its parent, swap them.
  3. Repeat until the element is in a valid position (either it reaches the root or its parent is smaller). This takes at most O(log n) swaps -- the tree height.

Heap Extract-Min (heappop)

  1. Save the root element (index 0) -- that's the minimum.
  2. Move the last element to the root position. This temporarily violates the heap property.
  3. Bubble down (sift down): Compare with children at indices 2i+1 and 2i+2. Swap with the smaller child if it's smaller than the current node.
  4. Repeat until the element is in a valid position. O(log n) swaps.

Array Representation

A heap is stored as a flat array. For element at index i:

  • Parent: (i - 1) // 2
  • Left child: 2*i + 1
  • Right child: 2*i + 2

E. The Code

import heapq

# Python's heapq is a MIN-heap. For max-heap, negate values.

# Basic operations
heap = []
heapq.heappush(heap, 5)    # Insert: O(log n)
heapq.heappush(heap, 3)
heapq.heappush(heap, 7)
smallest = heapq.heappop(heap)  # Extract-min: O(log n), returns 3
peek = heap[0]                    # Peek at min: O(1), returns 5

# K-th largest element: maintain a min-heap of size k
def kth_largest(nums, k):
    heap = nums[:k]
    heapq.heapify(heap)         # O(k) to build initial heap
    for num in nums[k:]:
        if num > heap[0]:       # bigger than smallest in top-k?
            heapq.heapreplace(heap, num)  # pop-and-push in one step
    return heap[0]              # smallest of the k largest = k-th largest

# Merge K sorted lists
def merge_k_sorted(lists):
    heap = []
    for i, lst in enumerate(lists):
        if lst:
            heapq.heappush(heap, (lst[0], i, 0))  # (value, list_idx, elem_idx)

    result = []
    while heap:
        val, li, ei = heapq.heappop(heap)
        result.append(val)
        if ei + 1 < len(lists[li]):
            heapq.heappush(heap, (lists[li][ei+1], li, ei+1))
    return result

F. When to Reach for This

K-th largest/smallest top K elements merge K sorted streaming median priority schedule by deadline closest points
G. Common Mistakes
  • Python heapq is min-heap only. For max-heap, negate: heappush(h, -val) and remember to negate back: -heappop(h).
  • Tuple comparison crash: When first elements tie, Python compares the second. If the second element isn't comparable (e.g., a ListNode), it crashes. Fix: use (value, unique_counter, object).
  • Confusing K-th largest with K-th smallest: For K-th largest, use a min-heap of size K (the root is the smallest of the K largest). For K-th smallest, use a max-heap of size K.
H. Memory Palace Anchor

Picture an old-school 8259 PIC chip on a motherboard. Interrupt lines come in from peripherals. The PIC doesn't sort them all -- it just always has the highest-priority one ready at its output pin. When the CPU acknowledges and handles that interrupt, the PIC instantly presents the next highest. Insert and extract, insert and extract. That's a heap.

Heap = priority interrupt controller. O(log n) to insert a new interrupt, O(log n) to serve and remove the highest priority one.

5. Monotonic Stack

Why "Monotonic Stack"?

"Monotonic" from Greek "monos" (single) + "tonos" (tone/direction). A function is monotonic if it only goes one direction (non-decreasing or non-increasing). The stack maintains this property — elements are always in one direction.

A. The Problem This Solves

For each element in an array, find the next greater element (or next smaller, previous greater, etc.) to its right or left. Also: largest rectangle in histogram, stock span, trapping rain water.

Why can't simpler approaches work? The brute force is O(n^2): for each element, scan right to find the first larger one. With a monotonic stack, each element is pushed and popped at most once, giving O(n) total.

Without this technique: "Daily Temperatures" with 30,000 days takes 900 million operations (brute force) vs 30,000 (monotonic stack).

B. The Core Insight

"Maintain a stack where elements are always in sorted order (monotonically increasing or decreasing). When a new element violates the order, pop -- each popped element has found its answer."

The stack holds "unresolved" elements waiting for their answer. Each pop resolves one.

EE Analogy: Peak Detector Circuit

A peak detector tracks the running maximum of a signal. When the voltage rises past the stored peak, the capacitor charges to the new peak. With a monotonic decreasing stack, it's similar: you maintain a "waterfall" of decreasing values. When a new value arrives that's taller than the top, the shorter values get "knocked off" -- they've found the first thing taller than them.

Think of it like a line of dominoes of decreasing height. When a new, taller domino appears, it knocks down all shorter ones. Each falling domino records who knocked it down (its "next greater element").

D. How It Works -- Step by Step

  1. Initialize an empty stack and a result array filled with -1. The stack will hold indices of elements whose "next greater" hasn't been found yet.
  2. Iterate through the array left to right.
  3. For each new element: while the stack is non-empty and the new element is greater than the element at the stack's top index, pop. The popped element's "next greater" is the current element. Record it in the result array.
  4. Push the current index onto the stack. This element is now "waiting" for its next greater element.
  5. After iteration, remaining indices in the stack have no next greater element (result stays -1).
  6. Key insight: each element is pushed exactly once and popped at most once. So the total work is O(2n) = O(n), not O(n^2).

E. The Code

def next_greater_element(nums):
    """For each element, find the next greater element to its right."""
    n = len(nums)
    result = [-1] * n
    stack = []  # stores INDICES; values at those indices are decreasing

    for i in range(n):
        # Current element is greater than stack top's element?
        # Then stack top has found its next greater element!
        while stack and nums[stack[-1]] < nums[i]:
            idx = stack.pop()
            result[idx] = nums[i]   # i is the answer for idx
        stack.append(i)

    return result
    # Example: [2,1,5,6,2,3] -> [5,5,6,-1,3,-1]

# Largest Rectangle in Histogram
def largest_rectangle(heights):
    stack = []  # increasing stack of indices
    max_area = 0
    heights.append(0)  # sentinel: force all remaining bars to be processed

    for i, h in enumerate(heights):
        while stack and heights[stack[-1]] > h:
            height = heights[stack.pop()]
            # Width extends from the bar after the new stack top to i-1
            width = i if not stack else i - stack[-1] - 1
            max_area = max(max_area, height * width)
        stack.append(i)

    heights.pop()  # remove sentinel
    return max_area

F. When to Reach for This

G. Common Mistakes
  • Confusing increasing vs decreasing stack: For "next greater," use a decreasing stack (pop when new element > top). For "next smaller," use an increasing stack (pop when new element < top). The name refers to the stack's order from bottom to top.
  • Forgetting the sentinel: In histogram problems, append a 0 at the end to force all remaining bars to be processed. Without it, bars still on the stack are never evaluated.
  • Width calculation in histogram: When you pop, the width is NOT i - popped_index. It's i - stack[-1] - 1 (distance to the next shorter bar on the left), or i if the stack is empty (extends all the way left).
H. Memory Palace Anchor

Picture a line of dominoes standing on a table, each one shorter than the previous. They form a nice staircase going down from left to right. Now a new, tall domino arrives on the right. It knocks down every domino shorter than itself -- each fallen domino records the tall one as its "next greater." The tall domino takes its place in the line, and the staircase property is maintained. That staircase IS the monotonic stack.

Monotonic stack = a domino staircase where new arrivals knock down everything shorter.

6. Union Find (Disjoint Set)

Why "Union-Find"?

Named after its two operations: Union (merge two groups) and Find (which group is this in?). Also called "Disjoint Set Union (DSU)" because it manages disjoint (non-overlapping) sets with union operations.

A. The Problem This Solves

Dynamically group elements into sets and efficiently query whether two elements are in the same group. Elements start separate, and you incrementally merge groups as connections are discovered. "Are nodes X and Y connected?" after adding edges one at a time.

Why can't BFS/DFS work? BFS/DFS can answer "are X and Y connected?" by traversing the graph. But if you add edges one at a time and ask the question after each addition, BFS/DFS rebuilds from scratch each time -- O(V+E) per query. Union-Find answers the same query in nearly O(1) amortized, and adding an edge is also nearly O(1).

Without Union-Find: Kruskal's MST algorithm would be O(E * V) instead of O(E * alpha(V)). Detecting if adding an edge creates a cycle would require a full graph traversal each time.

B. The Core Insight

"Represent each group as a tree. Two elements are in the same group if and only if they have the same root. Merging groups means linking one root to another."

With two optimizations (path compression + union by rank), every operation is nearly O(1).

EE Analogy: Breadboard Wire Jumpers

Imagine a breadboard with isolated pin groups. Each group of connected pins is a "set." When you add a wire jumper between two pin groups, the sets merge -- all pins in both groups are now connected. To check if two pins are connected, trace the wires to find which bus strip (root) each pin ultimately connects to. If it's the same bus strip, they're connected.

Path compression is like replacing a chain of jumper wires with a single direct wire to the bus strip. Union by rank is like always connecting the smaller group's bus to the larger group's bus, keeping the tree shallow.

D. How It Works -- Step by Step

  1. Initialize: Each element is its own root: parent[i] = i. Every element is a one-node tree. Also initialize rank (or size) to 0 (or 1).
  2. Find(x) -- find the root of x's tree: Follow parent pointers until you reach a node that is its own parent. That's the root. Path compression: While traversing, point every node directly to the root. This flattens the tree so future finds are O(1).
  3. Union(x, y) -- merge the sets containing x and y: Find the roots of x and y. If they're the same root, x and y are already connected -- return False. Otherwise, attach the shorter tree under the taller one (union by rank). This keeps trees balanced.
  4. Connected(x, y) -- check if x and y are in the same set: Simply check if find(x) == find(y).

Why Two Optimizations?

  • Without path compression: Trees can get tall, making find O(n) worst case.
  • Without union by rank: Merging can create degenerate chains (like a linked list).
  • With both: Amortized O(alpha(n)) per operation, where alpha is the inverse Ackermann function -- effectively constant (alpha(n) <= 4 for any practical n).

E. The Code

class UnionFind:
    def __init__(self, n):
        self.parent = list(range(n))   # each node is its own root
        self.rank = [0] * n            # tree height upper bound
        self.components = n            # number of disjoint sets

    def find(self, x):
        # Path compression: make every node point directly to root
        if self.parent[x] != x:
            self.parent[x] = self.find(self.parent[x])  # recursive flatten
        return self.parent[x]

    def union(self, x, y):
        px, py = self.find(x), self.find(y)
        if px == py:
            return False         # already in same set

        # Union by rank: attach shorter tree under taller tree
        if self.rank[px] < self.rank[py]:
            px, py = py, px      # ensure px is the taller root
        self.parent[py] = px      # py becomes child of px
        if self.rank[px] == self.rank[py]:
            self.rank[px] += 1   # only grows when equal height
        self.components -= 1
        return True

    def connected(self, x, y):
        return self.find(x) == self.find(y)

F. When to Reach for This

connected components are X and Y connected? merge groups redundant connection Kruskal's MST accounts merge cycle detection (undirected)
G. Common Mistakes
  • Forgetting path compression: Without it, find degrades to O(n) on tall chains.
  • Using both rank AND size: Pick one. Rank is an upper bound on tree height; size is the actual count of nodes. Mixing them corrupts the balancing.
  • String/object keys: When elements aren't integers (e.g., email addresses), use a dict for the parent map instead of a list.
H. Memory Palace Anchor

The strips merge into one connected group. When you need to check if pin D connects to pin B, you trace each one's wires to its bus strip (root). Same bus? Connected.

Path compression = replacing a chain of 5 jumper wires with one direct wire to the bus. Union by rank = always connecting the smaller strip to the larger bus, not the other way around.

7. Prefix Sum

Why "Prefix Sum"?

"Prefix" = the beginning portion. prefix_sum[i] = sum of all elements from index 0 to i (the prefix of the array up to position i). Named because each entry represents the sum of a prefix of the original array.

A. The Problem This Solves

Answering many range sum queries on an array. "What's the sum of elements from index 2 to index 7?" With Q such queries on an array of size n, brute force is O(Q*n). Prefix sum is O(n + Q) -- build once in O(n), then answer each query in O(1).

Why can't simpler approaches work? A single range sum query is already O(n). If you have Q queries, you'd repeat that work Q times. Prefix sum precomputes all cumulative sums so each query becomes a single subtraction.

Without prefix sum: "Count subarrays with sum K" would be O(n^2) or worse. With prefix sum + hash map, it's O(n).

B. The Core Insight

"Precompute cumulative sums so that any range sum is just one subtraction: sum(i..j) = prefix[j+1] - prefix[i]."

The sum of any window is the difference between two running totals.

EE Analogy: Voltage Integrator

A running voltage integrator (op-amp with capacitor feedback) accumulates the input signal over time. The output at time T is the integral from 0 to T. To find the integral from time A to time B, you subtract: V(B) - V(A). You don't re-integrate the segment -- you just read two values and subtract.

Prefix sum = discrete version of an integrator. Build the cumulative sum once, answer any "integral over [A, B]" with one subtraction.

D. How It Works -- Step by Step

  1. Build the prefix array. Create an array of size n+1. Set prefix[0] = 0. For each i from 0 to n-1: prefix[i+1] = prefix[i] + arr[i]. This is O(n).
  2. Answer a range query [L, R]. The sum of arr[L..R] (inclusive) = prefix[R+1] - prefix[L]. This is O(1) -- just a subtraction.
  3. Why prefix[0] = 0? It handles the edge case where L=0. Without it, you'd need special-case logic for queries starting at index 0.

Advanced: Count Subarrays with Sum K

  1. Maintain a running prefix sum and a hash map of {prefix_sum: count}.
  2. At each position, if prefix_sum - K exists in the map, those are subarrays ending here with sum K.
  3. Initialize the map with {0: 1} to account for subarrays starting at index 0.

E. The Code

# Basic prefix sum: O(1) range queries
def build_prefix_sum(arr):
    prefix = [0] * (len(arr) + 1)
    for i in range(len(arr)):
        prefix[i + 1] = prefix[i] + arr[i]
    return prefix

def range_sum(prefix, left, right):
    """Sum of arr[left..right] inclusive. O(1)."""
    return prefix[right + 1] - prefix[left]

# Advanced: count subarrays with sum exactly K
def subarray_sum_k(nums, k):
    count = 0
    prefix_sum = 0
    seen = {0: 1}   # critical: empty prefix sum = 0 occurs once

    for num in nums:
        prefix_sum += num
        # How many previous prefix sums equal (current - K)?
        # Each one marks the start of a subarray summing to K
        count += seen.get(prefix_sum - k, 0)
        seen[prefix_sum] = seen.get(prefix_sum, 0) + 1

    return count

F. When to Reach for This

subarray sum range sum query cumulative subarrays equal to K divisible by K contiguous array product except self
G. Common Mistakes
  • Off-by-one: The prefix array has n+1 elements. prefix[0] = 0, and the sum of arr[L..R] is prefix[R+1] - prefix[L], NOT prefix[R] - prefix[L].
  • Forgetting {0: 1} initialization: When counting subarrays with sum K, the empty prefix (sum=0) must be in the map with count 1. Without it, you miss subarrays that start at index 0.
  • Applying to products: Prefix sum doesn't directly work for products (zero ruins everything). Use prefix product with special handling for zeros, or use logarithms.
H. Memory Palace Anchor

Picture a digital multimeter measuring charge on a capacitor bank. Each capacitor in the row adds its charge to the running total. The meter reading at position 5 is the total charge from capacitors 0-4. To find the charge from capacitors 2-4, subtract the reading at position 2 from the reading at position 5. One subtraction instead of summing three values.

Prefix sum = capacitor bank integrator. Read two points, subtract, done.

8. Dijkstra's Shortest Path

Why "Dijkstra's Shortest Path"?

Named after Edsger Dijkstra, Dutch computer scientist. He invented it in ~20 minutes at a café in Amsterdam (1956), published 1959. Pronounced "DIKE-struh." The algorithm finds the shortest path from a source to all other nodes using a greedy, priority-queue approach.

A. The Problem This Solves

Finding the shortest path from a source node to all other nodes in a weighted graph where all edge weights are non-negative. This is the foundation of routing algorithms, navigation systems, and network optimization.

Why can't BFS work? BFS finds shortest paths in unweighted graphs (fewest edges). But with different edge weights, the path with fewest edges might not have the lowest total weight. Dijkstra accounts for weights.

Why not Bellman-Ford? Bellman-Ford handles negative weights but runs in O(V*E). Dijkstra is O((V+E) log V) -- much faster for large graphs. The tradeoff: Dijkstra only works with non-negative weights.

B. The Core Insight

"Greedily process the closest unvisited node. Once a node is processed, its shortest distance is final -- no future path through unvisited nodes can be shorter (because all remaining edges are non-negative)."

This greedy property only holds because edge weights are >= 0. One negative edge could create a shorter path through an unvisited node, breaking the invariant.

EE Analogy: Static Timing Analysis

In digital circuit design, static timing analysis (STA) computes the arrival time of signals at every gate. Each wire has a propagation delay (weight). The signal leaves the clock (source) and propagates outward. Each gate "latches" its arrival time when the signal first reaches it through the shortest delay path.

Dijkstra works the same way: the signal (shortest distance) propagates outward from the source. Nearby nodes get their final distance first, then the wavefront expands. Each node locks its distance when processed -- just like a gate's setup time is determined by the critical path.

D. How It Works -- Step by Step

  1. Initialize distances: dist[source] = 0, all others = infinity. Push (0, source) to the min-heap.
  2. Pop the minimum-distance node from the heap. This is the closest unfinished node.
  3. Check for staleness: If the popped distance is greater than the recorded dist[node], skip it -- we already found a shorter path (lazy deletion).
  4. Relax edges: For each neighbor, compute new_dist = dist[node] + weight. If new_dist < dist[neighbor], update dist[neighbor] and push (new_dist, neighbor) to the heap.
  5. Repeat until the heap is empty or the target is found.

Why "Lazy Deletion"?

When we find a shorter path to a node, we push a new entry to the heap but don't remove the old one (that would be O(n) in a binary heap). Instead, when we pop a stale entry, we just skip it. This is correct because the first time we pop a node, it's guaranteed to have the shortest distance.

E. The Code

import heapq
from collections import defaultdict

def dijkstra(graph, source):
    """Shortest path from source to all nodes.
    graph: {node: [(neighbor, weight), ...]}
    Returns: {node: shortest_distance}"""

    dist = defaultdict(lambda: float('inf'))
    dist[source] = 0
    heap = [(0, source)]    # (distance, node)

    while heap:
        d, node = heapq.heappop(heap)

        # Stale entry? We already found a shorter path.
        if d > dist[node]:
            continue

        # Relax all edges from this node
        for neighbor, weight in graph[node]:
            new_dist = d + weight
            if new_dist < dist[neighbor]:
                dist[neighbor] = new_dist
                heapq.heappush(heap, (new_dist, neighbor))

    return dict(dist)

# Example usage:
# graph = {
#     'A': [('B', 4), ('C', 1)],
#     'B': [('D', 5)],
#     'C': [('B', 2), ('D', 8), ('E', 3)],
#     'E': [('D', 2)]
# }
# dijkstra(graph, 'A')  -> {'A': 0, 'C': 1, 'B': 3, 'E': 4, 'D': 6}

F. When to Reach for This

shortest path (weighted) minimum cost path network delay time cheapest flights non-negative weights minimum effort path
G. Common Mistakes
  • Using with negative edges: Dijkstra does NOT work with negative edge weights. The greedy "finalize closest node" invariant breaks. Use Bellman-Ford instead.
  • Forgetting lazy deletion: If you don't skip stale heap entries (if d > dist[node]: continue), you process nodes multiple times and get wrong answers or TLE.
  • Confusing with BFS: BFS uses a regular queue and gives shortest path by EDGE COUNT. Dijkstra uses a priority queue (heap) and gives shortest path by WEIGHT SUM.
  • Not connecting to the heap pattern: Dijkstra's efficiency comes entirely from the min-heap. Without it, you'd scan all nodes to find the closest one -- O(V^2) total instead of O((V+E) log V).
H. Memory Palace Anchor

Picture the timing analysis view in a digital design tool. The clock edge launches from the flip-flop (source, distance 0). The signal propagates through combinational logic -- each gate adds its propagation delay. The tool shows arrival times at each node. Closer nodes lock their arrival times first, and the wavefront expands outward. A node's arrival time never decreases once set (because no gate has negative delay).

Dijkstra = static timing analysis. Source = clock. Edge weight = gate delay. Distance = arrival time. Non-negative weights = no negative gate delays.
